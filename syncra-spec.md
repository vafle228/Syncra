# Syncra — Спецификация проекта

> **Статус:** черновик v0.4 (собран в live-режиме вопрос/ответ)
> **Назначение документа:** дать code- и design-агентам полное и однозначное понимание продукта, его модели данных, протокола синхронизации и границ MVP.
> **Рабочее название:** Syncra (рабочее, зафиксировано).

---

## 1. Суть продукта

**Syncra** — децентрализованный (local-first) менеджер паролей с прямой P2P-синхронизацией между устройствами пользователя.

Ключевая идея: **у продукта нет сервера**. Пароли живут на устройствах пользователя и синхронизируются напрямую между ними, когда устройства находятся в одной локальной сети (за одним роутером). Пользователь владеет своими данными и не зависит от компании-провайдера.

### Что определяет продукт
- **Local-first:** каждое устройство хранит полную реплику данных и полностью работоспособно офлайн.
- **P2P-синхронизация:** без центрального сервера, без облака как обязательного компонента, без синхронизации через интернет.
- **Криптографическая идентичность:** доверие строится на парах ключей и сертификатах, а не на аккаунтах на сервере.
- **Глубокая платформенная интеграция:** автозаполнение паролей средствами ОС/браузера.

## 2. Модель доверия и идентичность

### 2.1. Идентичность устройства
- При инициализации хранилища устройство генерирует **пару ключей: приватный + публичный**.
- **Корень доверия — публичный ключ устройства (сертификат)**, а не сетевой идентификатор.
- MAC-адрес / ARP используются **только для обнаружения (discovery)** устройств в локальной сети. MAC легко подделывается и **не является основанием для доверия** — на него нельзя полагаться при аутентификации.

### 2.2. Сопряжение устройств (pairing)
- Новое устройство добавляется в список «устройств, с которыми можно синхронизироваться» вручную пользователем.
- Обмен публичными ключами при сопряжении защищается от MITM с помощью **QR-кода** (сканирование с одного устройства на другом переносит публичный ключ по доверенному внеполосному каналу).
- После сопряжения устройство запоминает: идентификатор (предварительно MAC — для discovery) + публичный ключ (для доверия).

### 2.3. Отзыв устройства (revoke)
- Обязательная функция (in scope). Сценарий: устройство украдено/потеряно.
- Пользователь может **отозвать** устройство из списка доверенных на остальных устройствах, после чего отозванное устройство больше не может синхронизироваться.
- **Распространение отзыва — по той же схеме, что и синхронизация паролей** (revoke-запись расходится по сети доверия при следующих сеансах синхронизации).
- **Реалистичная оценка гарантий (важно для code-агента, не переоценивать роль revoke):**
  - В децентрализованной сети отзыв **не решается на 100%** — это принятое ограничение MVP.
  - Украденное устройство **уже имеет полную реплику всех паролей на диске** на момент кражи. Revoke отрезает его от *будущих* синхронизаций, но **не спасает уже имеющиеся у него данные**.
  - **Настоящая линия обороны при краже — шифрование at-rest** (§3.1): без мастер-пароля/биометрии БД не открывается. Revoke — это дополнительный механизм «отрезать от будущего», а не основная защита.
  - Расчёт для MVP: в ~99% случаев revoke успеет распространиться по сети доверия раньше, чем злоумышленник получит доступ. Для MVP этого достаточно.

## 3. Модель шифрования

Различаем **два независимых уровня шифрования**:

### 3.1. At rest (локальное хранилище)
- Локальная БД шифруется ключом, выведенным из **мастер-пароля** (или разблокируется через биометрию/PIN — см. §7).
- Пароли в БД хранятся как **зашифрованная строка** (предположительно с солью).

### 3.2. In transit (синхронизация)
- При передаче данных другому устройству полезная нагрузка шифруется **на публичный ключ получателя**.
- Только устройство-получатель со своим приватным ключом может расшифровать переданные записи.

## 4. Модель данных

### 4.1. Запись пароля (Password Record)

**Единица данных всей системы — запись (`record`).** Именно запись синхронизируется, имеет tombstone и участвует в разрешении конфликтов. Никаких сущностей «выше» записи в MVP нет (см. §4.4 про несколько аккаунтов).

Поля делятся на два класса:

- **🔒 Секретные** — шифруются на уровне поля, показываются пользователю только по явному «reveal», не держатся расшифрованными в памяти без необходимости.
- **Метаданные** — лежат открыто *внутри* и без того зашифрованной БД (§3.1); видны в списке/поиске, используются для матчинга и синхронизации.

| Поле | Класс | Обяз. | Назначение |
|---|---|---|---|
| `record_id` (UUID) | метаданные | да | **Стабильный уникальный идентификатор.** Генерируется при создании, не меняется никогда. Ключ синхронизации и разрешения конфликтов. |
| `vault_id` | метаданные | да | Ссылка на секцию/vault (см. §4.2). |
| `service_name` | метаданные | да | Отображаемое имя сервиса. **Не уникально** и не используется для матчинга автозаполнения — только для показа. |
| `urls[]` | метаданные | да (≥1 для автофила) | **Список URL/доменов** для матчинга автозаполнения. Список, а не одно поле: у сервиса бывает несколько доменов входа (`login.x.com`, `account.x.com`). Основа автозаполнения (§7.2). |
| `login` | метаданные | да | Логин пользователя. |
| `account_label` | метаданные | нет | Человекочитаемая метка аккаунта («личный», «рабочий»). Нужна, чтобы различать несколько аккаунтов одного сервиса в пикере автозаполнения (§4.4). |
| `password` | 🔒 секрет | да | Пароль пользователя (шифруется, возможно с солью). |
| `notes` | 🔒 секрет | нет | Свободные заметки: контрольные вопросы, коды восстановления, PIN и т.п. |
| `totp_secret` | 🔒 секрет | нет | Секрет для генерации 2FA/TOTP-кодов. **Поле заводится в MVP-схему сразу**, сам генератор кодов может появиться в фазе 2 (см. ниже). |
| `version` | метаданные | да | **Счётчик версий.** Инкрементируется при каждом изменении. Основной механизм сравнения свежести (§5.2). |
| `created_at` | метаданные | да | Дата создания. Неизменяема (нулевой риск конфликта). Сортировка, «возраст записи». |
| `updated_at` | метаданные | да | Дата последнего изменения любого поля. Для показа и как вторичный сигнал. |
| `password_updated_at` | метаданные | да | Дата последнего изменения **именно пароля** (отдельно от `updated_at`). Гигиена: подсветка «паролю пора на ротацию». |
| `deleted_at` | метаданные | — | Дата удаления (tombstone). `null` для живых записей (§5.4). |

> **Почему UUID, а не имя сервиса:** имя сервиса не уникально. Если бы ключом было имя, второй аккаунт на `google.com` затёр бы первый. Все операции синхронизации и разрешения конфликтов идут по `record_id`.

> **Про TOTP:** поле `totp_secret` закладывается в схему на старте намеренно. Причина — докрутить новое **секретное** поле в уже синхронизируемую зашифрованную схему позже означает миграцию зашифрованных данных на всех устройствах (дорого). Само вычисление TOTP-кодов — задача, которую можно вынести в фазу 2.

**Сознательно НЕ включено в MVP** (и почему):
- **Вложения/файлы** — противоречат принципу «минимизируем трафик синка»; отдельная подсистема хранения блобов. Не в этом продукте.
- **Теги** — дублируют vaults на текущем масштабе; чистое аддитивное поле, безопасно добавить потом.
- **Кастомные key-value поля** — почти всё закрывают `notes` без вариативной схемы и лишней UI-сложности.
- **История паролей** (под-коллекция версий) — пост-MVP; базовую потребность частично закрывает показ «какая версия раньше» при конфликте (§5.5).
- **Иконки/фавиконы** — не поле БД, а рендер на клиенте. Тянуть фавикон из интернета = утечка «какими сервисами пользуешься» стороннему провайдеру, что идейно неверно для local-first. Задача дизайна (локальные заглушки/буквы).
- **`item_type` (карты/заметки/удостоверения)** — Syncra остаётся сфокусированным менеджером **паролей**. Дискриминатор типа не вводим (можно заложить позже, если продукт решит расширяться).

### 4.2. Секции / Vaults
- Пользователь может организовать пароли в **секции (vaults)** — например, «личное» и «рабочее».
- По умолчанию секции живут **в одном пространстве**: при автозаполнении система предлагает подходящий пароль **независимо от того, в каком vault он лежит**.
- Пользователь может разделять секции, если это нужно.
- **Синхронизация настраивается на уровне секций:** в настройках можно указать, какие секции синхронизируются между устройствами, а какие остаются локальными. При этом сам стор (набор данных секции) **идентичен** между всеми устройствами, которые её синхронизируют.

### 4.3. Хранилище
- Локальная БД — предположительно **SQLite3**.
- Каждое устройство хранит **полную реплику** синхронизируемых секций.

### 4.4. Несколько аккаунтов на одном сервисе (согласованная модель — Вариант A)

Частый и **первоклассный** сценарий, а не крайний случай: у пользователя несколько аккаунтов на одном сервисе (личный и рабочий `google.com` и т.п.).

**Согласованная модель — «плоская» (Вариант A):**
- Каждый аккаунт — это **самостоятельная запись** со своим `record_id`. Никакой сущности-контейнера «сервис» над записями **не вводится**.
- `{service_name / urls}` **намеренно не уникальны** — это опора продукта, а не коллизия.
- Группировка нескольких аккаунтов одного сервиса — **чисто UX/UI-аспект** (визуально показываем их вместе, различаем по `login` и `account_label`). В модели данных и в протоколе синхронизации — **ноль изменений**.

**Почему не «Вариант B» (сущность «сервис» с вложенными аккаунтами):** он удвоил бы модель данных и сломал уже согласованную логику синхронизации/конфликтов/tombstones (что делать при удалении сервиса с N аккаунтами; как мержить конфликт «на одном устройстве добавили аккаунт, на другом переименовали сервис»). Это ровно тот CRDT-класс сложности, которого проект сознательно избегает. Вариант A даёт весь нужный UX без изменений в синке.

**Поведение при совпадении нескольких записей** (правило матчинга — см. также §7.2):
- Матчинг по URL/домену может вернуть **несколько записей** → система **показывает пикер** и даёт пользователю выбрать. Система **не угадывает** аккаунт сама.
- **Запоминание выбора для конкретной страницы** («на этом сайте по умолчанию предлагай рабочий») — **в MVP не входит** (решение принято по умолчанию; чтобы включить — потребуется отдельное синкаемое поле «страница → предпочтённый аккаунт»).

## 5. Протокол синхронизации

### 5.1. Обнаружение
- Синхронизация работает **только в пределах одной локальной сети** (устройства за одним роутером, один L2-сегмент).
- Синхронизация **через интернет / между разными сетями не поддерживается** (осознанное решение: сохраняет смысл P2P и убирает лишнюю сложность).
- Обнаружение новых устройств — предварительно по **ARP-пакетам**.

### 5.2. Определение «свежести» записи
- Основной машинный критерий — **`version` (счётчик версий)**: работает всегда и полностью локально, не зависит от расхождения часов между устройствами.
- **`updated_at`** хранится параллельно — для отображения пользователю и как вспомогательный сигнал.
- **TSP / доверенный сервер времени — опциональное улучшение**, не входит в core-логику. Может использоваться, чтобы показать пользователю достоверную дату, когда есть интернет. Core-логика сравнения на него **не завязывается**, чтобы не нарушать принцип «всё локально».

### 5.3. Алгоритм обмена (дифференциальный)

Цель — минимизировать объём данных в сети и не гонять пароли лишний раз.

1. Устройство, инициирующее синхронизацию, отправляет **компактный манифест**: список пар `{record_id, version}` (+ `updated_at`) по своим записям.
2. Устройство-партнёр сравнивает манифест со своим состоянием и определяет, по каким записям у него **более свежая версия**.
3. Партнёр отправляет обратно **только дифф** — записи, которых у инициатора нет или которые у него устарели. Уже актуальные на устройстве данные повторно не передаются.
4. Передаваемые записи шифруются на публичный ключ получателя (§3.2).

> Синхронизация в обе стороны симметрична: каждое устройство в итоге получает недостающее/более свежее от другого.

### 5.4. Удаление (tombstones)
- Удаление так же важно, как добавление.
- Удалённая запись превращается в **надгробие (tombstone)**: сохраняются `record_id` + `deleted_at` (+ `version`), сами данные удаляются.
- Tombstone распространяется при синхронизации, чтобы запись не «воскресла» с другого устройства.
- **Срок жизни надгробий: ~30 дней.** Обоснование: в ~99% случаев цикл синхронизации происходит не реже, чем раз в 24 часа (пользователь приходит домой в одну сеть). 30 дней надёжно покрывают риск «воскрешения» пароля. Совсем не чистить — не вариант (рост БД).

### 5.5. Разрешение конфликтов
- Конфликт = одна и та же запись (`record_id`) независимо изменена на двух устройствах.
- **Разрешение на уровне целой записи, выбор делает пользователь.** Система показывает **полный diff** обеих версий; пользователь выбирает **одну версию целиком** (не сборку по полям).
- В редких случаях (~1%), когда нужна ручная пересборка, пользователь видит полный diff и может вручную собрать нужные данные.
- **Историю времени сохраняем:** пользователь видит, какая версия была раньше, какая позже.

### 5.6. Транспорт
- Синхронизация реализуется как **собственный протокол прикладного уровня поверх TCP** (TCP выбран ради гарантии доставки).
- Точный контракт протокола (структура манифеста, установление сессии, шифрование канала, обработка обрывов и повторов) прорабатывается совместно с code-агентом.

## 6. Функции менеджера паролей

### 6.1. Генератор паролей (in scope)
- Настраиваемый генератор: набор символов, длина и т.п.
- **UX-принцип:** пользователь настраивает параметры **один раз** (сохранённый профиль генерации), а не при каждом использовании.
- При генерации пользователь указывает `n`, и генератор выдаёт **n вариантов** пароля на выбор.

### 6.2. Экспорт / Импорт / Бэкап

**Две разные задачи — два разных экспорта:**

| Тип | Назначение | Формат | Безопасность |
|---|---|---|---|
| **CSV-экспорт (миграция)** | Перенос в другой менеджер / разовое использование | CSV с **расшифрованными** данными, отдаётся после ввода мастер-пароля | ⚠️ Опасный артефакт. Обязательное предупреждение пользователю: «файл не зашифрован, удалите после использования». |
| **Зашифрованный экспорт (бэкап)** | Резервная копия на случай потери всех устройств | Файл, **зашифрованный мастер-паролем** | Безопасно хранить в облаке / на флешке. Восстанавливается вводом мастер-пароля. |

- **Импорт (jump-start):** импорт из других менеджеров паролей (браузерные / сторонние приложения) для быстрого старта.

### 6.3. Восстановление доступа
- **Основной путь:** данные восстанавливаются с любого другого спаренного устройства (полная реплика).
- **Резервный путь:** зашифрованный бэкап-файл (§6.2), если все устройства потеряны.
- CSV-экспорт как таковой резервным путём для «утопленного устройства» **не считается** — для этого зашифрованный бэкап.

## 7. Платформы и интеграция

### 7.1. Целевые платформы

| Платформа | Статус | Роль |
|---|---|---|
| iPhone (iOS) | 100% в скоупе | Мобильный клиент + AutoFill |
| Windows | 100% в скоупе | Десктоп-клиент |
| Linux | 100% в скоупе | Десктоп-клиент |
| Браузерное расширение | 100% в скоупе | Реализует десктопную интеграцию/автозаполнение |
| Android | **Вне скоупа** | Пока не планируется |
| macOS | Не заявлено | — |

### 7.2. Автозаполнение (AutoFill)
- «Глубокая интеграция» = приложение предлагает вставить пароль в других приложениях/браузерах.
- iOS: **AutoFill Credential Provider**.
- Десктоп: **браузерное расширение** (основной механизм десктопной интеграции).
- При автозаполнении подходящий пароль предлагается **независимо от vault**, в котором он лежит (§4.2).
- **Матчинг идёт по `urls[]`/домену, а не по `service_name`.** `service_name` — только отображаемое имя.
- **Несколько совпадений → пикер.** Если под страницу подходит несколько записей (несколько аккаунтов одного сервиса, §4.4), система показывает список на выбор и **не угадывает** сама. Записи в пикере различаются по `login` и `account_label`. Запоминание выбора для страницы в MVP не входит.

### 7.3. Разблокировка (unlock)
- iOS: Face ID / Touch ID / пароль телефона.
- Десктоп: PIN-код.
- **Универсальный фолбэк на всех платформах: мастер-пароль.**

> **Связка биометрии и мастер-пароля (решено):**
> - **Мастер-пароль — первичен и обязателен.** Прежде чем включить биометрию, пользователь вводит мастер-пароль.
> - **Биометрия — это удобство, а не отдельный секрет:** способ не вводить мастер-пароль каждый раз при доступе к базе.
> - Технически: биометрия/PIN разблокирует ключ, лежащий в защищённом хранилище платформы (iOS Keychain / Secure Enclave, аналоги на десктопе), который даёт доступ к расшифровке БД. Мастер-пароль остаётся универсальным фолбэком на всех платформах.

## 8. Технологический стек и архитектура

> Верхнеуровневое описание. Конкретные версии библиотек, имена крейтов и детали API финализирует code-агент; здесь зафиксированы принятые решения и границы ответственности слоёв.

### 8.1. Стек

| Слой | Технология | Роль |
|---|---|---|
| Оболочка / рантайм | **Tauri 2** | Единый каркас на десктоп (Windows, Linux) и мобилку (iOS) из одной кодовой базы. Нативный webview вместо бандла Chromium: WebView2 (Windows), WebKitGTK (Linux), WKWebView (iOS). |
| Ядро (backend-логика) | **Rust** | Вся security-критичная и платформонезависимая логика: крипта, сеть, хранилище, синхронизация. Общее для всех платформ. |
| UI (фронтенд) | **JavaScript/TypeScript + Vue (SPA)** | Единая «морда» для всех платформ. Только представление и взаимодействие. Общается с ядром через Tauri IPC (commands/events). |
| iOS-интеграция | **Swift** (нативное расширение) | AutoFill Credential Provider Extension — обязательно нативно, требование Apple (см. §8.4). |
| Десктоп-автозаполнение | **Браузерное расширение** (отдельный JS/TS-проект, WebExtension) | Общается с запущенным десктоп-приложением (см. §8.4). |

**Инструментарий сборки:** Cargo (Rust), Vite (сборка Vue SPA), Tauri CLI (упаковка под платформы). Для сборки под iOS дополнительно требуется **macOS + Xcode + платный Apple Developer аккаунт** (без них iOS-таргет и entitlements недоступны).

**Категории библиотек ядра** (конкретику выбирает code-агент, здесь — направление):
- **Криптография:** проверенные крейты для подписи и обмена ключами (класс Ed25519/X25519), AEAD-шифрование (класс ChaCha20-Poly1305/AES-GCM), KDF из мастер-пароля (класс Argon2/scrypt). Не изобретать своё.
- **Хранилище:** SQLite (класс `rusqlite`/`sqlx`); шифрование at-rest — на уровне полей и/или через SQLCipher (решение code-агента).
- **Сеть/обнаружение:** TCP из стандартного/async-стека Rust; обнаружение пиров в LAN (ARP/mDNS).

### 8.2. Принцип разделения ответственности

Главное правило архитектуры: **UI ничего не знает о секретах и сети. Всё security-критичное живёт в Rust-ядре и никогда не покидает его в открытом виде.**

- **Vue-фронтенд** рисует, обрабатывает ввод, показывает состояния (reveal, синхронизация, конфликт). Он запрашивает у ядра данные для отображения и отдаёт команды пользователя. Расшифрованный секрет попадает в UI только в момент явного reveal/копирования и не хранится.
- **Rust-ядро** держит ключи, выполняет шифрование/дешифрование, ведёт БД, гоняет протокол синхронизации, делает discovery, проверяет доверие устройств. Приватный ключ и производный ключ шифрования БД не уходят в webview.

### 8.3. Модули Rust-ядра (общие для всех платформ)

| Модуль | Ответственность |
|---|---|
| **Crypto** | Генерация пары ключей устройства; вывод ключа БД из мастер-пароля (KDF); пофайловое/пополевое шифрование секретов at-rest (§3.1); шифрование данных на публичный ключ получателя при синхронизации (§3.2). |
| **Storage** | SQLite-хранилище: записи, версии, tombstones, секции, список доверенных устройств и их публичных ключей. Полная реплика синхронизируемых секций. |
| **Sync engine** | Дифференциальный протокол (§5.3): формирование манифеста `{record_id, version}`, вычисление диффа, обнаружение и подготовка конфликтов. Поверх TCP (§5.6). |
| **Discovery** | Обнаружение пиров в локальной сети (ARP/mDNS). Только discovery — доверие проверяется отдельно по ключам. |
| **Trust** | Pairing (генерация/разбор QR-пейлоада с публичным ключом), хранилище сертификатов/публичных ключей, revoke и его распространение (§2.3). |
| **Generator** | Логика генератора паролей: профиль настроек + выдача N вариантов (§6.1). |
| **Import/Export** | CSV (миграция) и зашифрованный бэкап (§6.2). |

### 8.4. Три точки платформенной интеграции (тонкие, пишутся под платформу)

Всё остальное переиспользуется; отдельно под платформу пишутся только эти три:

1. **iOS AutoFill Credential Provider Extension (Swift).** Системное автозаполнение на iPhone возможно только через нативное расширение приложения с entitlement `autofill-credential-provider` (требует платного Apple-аккаунта и раздачи через App Store). **Ключевой архитектурный нюанс:** расширение работает в отдельном песочном процессе, поэтому хранилище должно лежать в **общем App Group контейнере**, а ключ дешифровки — быть доступен расширению через **общий Keychain access group**, разблокируемый биометрией. Это проектируется отдельно (см. Открытые вопросы).
2. **Браузерное расширение (отдельный JS/TS-проект).** Реализует десктопное автозаполнение. Само хранилище не держит — обращается к запущенному десктоп-приложению Syncra (через native messaging или локальный IPC) за подходящими записями и отдаёт выбранный пользователем вариант (пикер, §7.2). Транспорт связи «расширение ↔ приложение» — задача проработки.
3. **Разблокировка и хранение ключей под платформу.** Биометрия/PIN (плагин биометрии Tauri на iOS: Face ID/Touch ID; PIN на десктопе), хранение ключа в защищённом хранилище платформы (iOS Keychain/Secure Enclave, аналоги на десктопе), а также entitlements на доступ к локальной сети под iOS (`NSLocalNetworkUsageDescription` + multicast).

### 8.5. Типовые потоки данных (для наглядности)

- **Разблокировка:** пользователь вводит мастер-пароль (первый раз) или подтверждает биометрией → платформенное хранилище отдаёт ядру ключ → Crypto открывает БД. UI получает только «разблокировано/нет».
- **Показ пароля (reveal):** UI шлёт в ядро команду «дай секрет записи X» → Crypto дешифрует → значение отдаётся в UI на момент показа/копирования.
- **Синхронизация:** Discovery нашёл пир в LAN → Trust проверил, что он доверенный (по ключу) → Sync engine обменялся манифестами → передал только дифф, зашифрованный на публичный ключ пира → Storage применил изменения, при расхождении подготовил конфликт для UI.
- **Автозаполнение (iOS):** нативное расширение читает из общего контейнера, при неоднозначности показывает системный пикер (§7.2). На десктопе аналогично, но через браузерное расширение ↔ приложение.

### 8.6. Что переиспользуется, а что нет

- **Переиспользуется на всех платформах:** весь Vue UI + всё Rust-ядро (§8.3).
- **Пишется отдельно под платформу:** только три точки интеграции (§8.4).
- Это не «отдельные приложения под десктоп и телефон», но и не «одно на всё»: общий UI + общее ядро + тонкий нативный слой на каждую платформу.

## 9. Границы MVP

Синхронизация первична, но релиз без автозаполнения не планируется. Поэтому две фазы:

### MVP 1 — Синхронизация (десктоп)
- Инициализация хранилища, генерация ключей.
- Pairing через QR-код.
- P2P discovery + дифференциальная синхронизация в локальной сети.
- CRUD паролей, секции, разрешение конфликтов, удаление (tombstones).
- Генератор паролей, экспорт/импорт/бэкап.
- Проверка алгоритма синхронизации в **десктоп-среде** (Windows/Linux + расширение).

### MVP 2 — Автозаполнение и другие платформы
- iOS-клиент.
- AutoFill на iOS и через браузерное расширение на десктопе.
- Проверка автозаполнения на разных платформах.

## 10. Решённые ранее вопросы (зафиксировано)

Эти пункты были открытыми в v0.1 и закрыты в v0.2:

- ✅ **Биометрия ↔ ключ шифрования.** Мастер-пароль первичен и обязателен; биометрия — удобство поверх него (см. §7.3).

- ✅ **Нейминг.** Syncra — рабочее, зафиксировано.
- ✅ **Транспорт синхронизации.** Собственный протокол поверх **TCP** (гарантия доставки). Точный контракт — с code-агентом (см. §5.6).
- ✅ **Схема полей записи.** Финализирована с разбивкой на секретные/метаданные (см. §4.1).
- ✅ **Несколько аккаунтов на одном сервисе.** Согласован Вариант A (плоская модель, группировка — только UX), см. §4.4.
- ✅ **Стек и оболочка.** Rust-ядро + Vue SPA под каркасом **Tauri 2** (десктоп + iOS из одной базы); три тонкие точки нативной интеграции (см. §8).

## 12. Глоссарий

- **Local-first** — данные первично живут на устройстве и полностью работоспособны без сети/сервера.
- **P2P-синхронизация** — прямой обмен данными между устройствами без посредника-сервера.
- **Vault / Секция** — логическая группа паролей (напр. «личное», «рабочее»).
- **Tombstone (надгробие)** — метка удаления записи, распространяемая при синхронизации, чтобы удалённая запись не «воскресла».
- **Version (счётчик версий)** — монотонный счётчик изменений записи; основной критерий сравнения свежести, устойчивый к расхождению часов.
- **Pairing** — процесс сопряжения двух устройств с обменом публичными ключами (через QR).
- **Revoke** — отзыв устройства из доверенных.
- **AutoFill** — автозаполнение учётных данных средствами ОС/браузера.
- **Tauri** — каркас для приложений с web-фронтендом и нативным ядром; использует системный webview вместо бандла браузера. Здесь — Tauri 2 (десктоп + iOS из одной базы).
- **Rust-ядро** — общий для всех платформ нативный слой Syncra: крипта, хранилище, синхронизация, discovery, доверие.
- **IPC (Tauri)** — канал вызовов между Vue-фронтендом и Rust-ядром (commands/events).
- **App Group / Keychain access group** — механизмы iOS для общего доступа к данным и ключам между приложением и его расширением; нужны, чтобы AutoFill-расширение видело хранилище и ключ.
- **AutoFill Credential Provider Extension** — нативное iOS-расширение, регистрирующее приложение как поставщика паролей для системного автозаполнения.
