## 1. Где мы находимся

Фронтенд закрывает контракт целиком и оттестирован против фейк-ядра. Настоящее ядро закрывает
жизненный цикл хранилища, записи, секции, генератор, настройки безопасности, доверие,
сопряжение, обнаружение соседей в LAN и защищённый транспорт между ними — то есть **менеджер
паролей, который находит второе устройство, доверяет ему по ключу и умеет с ним говорить, но
пока не рассказывает ему ни одной записи**. Обмен начинается с S4.

Материальный след разрыва — макрос `not_ready![…]` в конце
[`crates/syncra-app/src/commands.rs`](crates/syncra-app/src/commands.rs): десять команд контракта
отвечают «Эта часть ядра ещё не готова», а `list_conflicts` отдаёт честный, но пустой список.

| Область | Состояние ядра |
|---|---|
| F3 замок · F4/F5 записи · F6 генератор · F7 секции · F13 безопасность | **готово** |
| **F9 доверие и отзыв** | **готово** (S1): пара ключей устройства, таблица `devices`, `list_devices` / `revoke_device` |
| **F8 сопряжение** | **готово** (S2 + S3): QR кодирует ядро, пейлоад подписан, SAS из ключей обеих сторон, запись пира в `devices`; ручной код ищет устройство в LAN, `device_paired` уходит показавшей стороне |
| **F10 синхронизация** | **наполовину** (S3): discovery и транспорт есть, манифеста и диффа нет |
| **F11 конфликты** | нечему конфликтовать: расхождения не обнаруживаются |
| **F12 импорт/экспорт/бэкап** | нет ни CSV, ни бэкапа, ни парсеров |
| События ядра | эмитятся `unlocked`, `locked`, `peer_found`, `device_paired`, `sync_status`; `conflict_raised` не существует (S5) |

Долги, названные в самом коде и в спеке, но не закрытые:

- **Метаданные лежат в файле открытым текстом.** `service_name`, `login`, `urls` не шифруются;
  обещание держит видимым тест `tests/at_rest.rs::metadata_is_deliberately_not_encrypted_in_this_step`.
  §3.1 спека обещает шифрование БД — см. **S7.1**.
- **Надгробия копятся вечно:** GC на 30 дней (§5.4) нет — см. **S7.2**.
- **PIN завести нечем:** `unlock_with_pin` всегда отказывает, команды энролмента нет в контракте — **S7.3**.
- **Флаг `vaults.sync` в схеме есть, но его никто не читает** — он оживает в **S4**.
- **Публичный ключ подписи едет в приветствии открытым текстом** — наблюдатель в LAN видит,
  что это то же устройство, что и вчера. §11 спека держит вопрос открытым; MVP 1 его не
  закрывает (обоснование — в шапке `src/net/handshake.rs`).

## 2. Правила, общие для всех задач

**Закон №1 остаётся законом.** Открытый текст пересекает границу IPC ровно в трёх командах:
`get_secret`, `get_conflict_secret`, `generate_passwords`. Четвёртой не появляется. Экспорт файл
**собирает и пишет сам** — наружу уходит `ExportFile` с путём, а не содержимое.

**Эталон — фейк-ядро.** Прежде чем спорить с ним, перечитайте `../client/src/core/mock/`. Если ядру
нужно другое поведение, это изменение **контракта**: правится `contract.ts`, согласуется с
фронт-агентом и отмечается в его `TASKS.md` — молча разойтись нельзя.

**Крипту не изобретаем.** Только проверенные крейты из категорий §8.1. Новые зависимости — по
согласованию: список в `[workspace.dependencies]` curated, туда не досыпают.

**Ошибки уходят прямо в UI.** В `message` не должно быть ни путей к хранилищу, ни ключей, ни
адресов в сети, ни текста ошибок SQLite (см. `src/error.rs`).

**Ядро не знает про Tauri.** Всё, что требует платформы — путь к файлу, имя хоста, системный диалог
выбора файла, — приходит в ядро готовым аргументом от оболочки.

### Definition of Done каждой задачи

1. `cargo test` — зелено; новая логика покрыта тестами в `crates/syncra-core/tests/`.
2. `cargo clippy --all-targets -- -D warnings` — чисто.
3. `cargo fmt --all -- --check` — чисто.
4. Соответствующие строки убраны из `not_ready![…]`, команды зарегистрированы в
   `crates/syncra-app/src/lib.rs`.
5. Раздел «Что готово» в `README.md` обновлён; закрытая «граница шага» переписана, а не оставлена врать.

### S1 — Идентичность устройства и таблица доверия (F9, §2.1 · §2.3) ✅ СДЕЛАНО

> Раздел оставлен как есть — по нему читается, **почему** всё устроено так. Что получилось:
> `src/crypto.rs::DeviceKeypair` (Ed25519 + X25519, один запечатанный секрет),
> `src/trust.rs`, `MIGRATION_2` с цепочкой миграций, `tests/trust.rs`.
> Отличие от написанного ниже: приватный ключ заводит не только `init_vault`, но и `unlock` —
> хранилищу схемы 1 его при миграции взять неоткуда, ключ хранилища появляется только при отпирании.

Фундамент всего остального: без пары ключей нет ни сопряжения, ни защищённого канала, ни доверия.
Сегодня в `meta` лежит только `device_id` (UUID) — идентификатор без единого ключа за ним.

**Крипта** (`src/crypto.rs`, рядом с Argon2/XChaCha20): подпись — класс Ed25519, обмен ключами —
класс X25519 (§8.1). Одна долговременная пара на устройство.

**Хранение ключа.** Пара генерируется в `Core::init_vault` (`src/session.rs`) в той же транзакции,
что и остальная инициализация. Приватный ключ ложится в `meta` **запечатанным ключом хранилища**
(`crypto::seal` с собственным AAD, напр. `syncra:device:secret`), публичный — открыто. То есть
приватный ключ устройства защищён мастер-паролем ровно так же, как пароли: украденный файл не даёт
права представляться этим устройством.

> ⚠️ **Не забыть:** `Core::change_master_password` перешифровывает хранилище через
> `records::rekey_all`, который знает только про записи. Приватный ключ обязан перешифровываться
> **в той же транзакции**. Пропустить это — значит терять идентичность устройства при каждой смене
> пароля, и заметить это удастся только в сети, через неделю.

**Схема, миграция 2** (`src/storage/schema.rs`): поднять `SCHEMA_VERSION`, добавить `MIGRATION_2` и
применять миграции по цепочке от записанной в `meta` версии — сейчас `migrate()` просто исполняет
единственный батч, и этого больше не хватит.

```sql
CREATE TABLE devices (
  device_id         TEXT PRIMARY KEY,
  name              TEXT NOT NULL,
  kind              TEXT NOT NULL,      -- 'desktop' | 'mobile'
  public_key        BLOB NOT NULL,      -- корень доверия (§2.1)
  fingerprint_words TEXT NOT NULL,      -- JSON: слова, сверенные при сопряжении
  paired_at         TEXT NOT NULL,
  last_seen_at      TEXT,
  revoked_at        TEXT                -- NULL у действующих
);
```

**Новый модуль** `src/trust.rs` (§8.3 «Trust»): чтение и запись доверенных устройств, проверка
«доверен ли этот публичный ключ», отметка `last_seen_at`.

**Команды.** `list_devices`, `revoke_device`:

- своё устройство всегда в списке, `is_this_device: true`; ни ключа, ни MAC в `Device` нет;
- **себя отозвать нельзя** → `VALIDATION`: устройство в руках — единственное, что у человека точно есть;
- отзыв **идемпотентен** и не переписывает `revoked_at`: момент отзыва — факт, а не текущее значение;
- отозванные из списка **не исчезают**: человек должен видеть, что ноутбук отозван, а не что его не было.

**Имя устройства** берёт оболочка (hostname) и передаёт ядру — как и путь к БД.

**Тесты:** `tests/trust.rs` — ключ переживает `lock`/`unlock` и смену мастер-пароля; отзыв себя
отбивается; повторный отзыв возвращает прежний `revoked_at`; хранилище схемы 1 доезжает миграцией
без потери данных.

### S2 — Сопряжение через QR (F8, §2.2) ✅ СДЕЛАНО

> Раздел оставлен как есть — по нему читается, **почему** всё устроено так. Что получилось:
> `src/pairing.rs` (формат пейлоада, base32, подпись Ed25519, QR через крейт `qrcode`),
> `trust::pair_fingerprint` и `trust::upsert_peer`, сеанс в памяти `Core`, `tests/pairing.rs`.
> Пейлоад — `SYNCRA-PAIR:<КОД6>.<base32>`: прописные и base32 ради `alphanumeric mode` QR,
> внутри версия формата, имя и тип устройства, публичный ключ, одноразовый ключ сеанса и
> подпись над всем этим вместе с кодом. Контракт не менялся: строка пейлоада границу IPC не
> пересекает, и фронт её формата не знает.
>
> **Три отличия от написанного ниже** — все были из-за того, что сети ещё нет. **Первые два
> закрыты в S3**, третье осталось:
>
> - ~~**шесть символов, набранные руками, ключа не несут**~~ — несут по-прежнему не ключ, а
>   имя сеанса, но теперь по нему устройство и правда ищут в LAN (`net::Node`). Формулировка
>   `NOT_FOUND` осталась дословно та же: изменилось только то, кто её даёт;
> - ~~**`device_paired` не эмитится**~~ — уходит показавшей стороне по сети, из
>   `net::announce_pairing`. Локально из `confirm_pairing` его по-прежнему не шлют: это было
>   бы эхо собственного ответа команды;
> - **через десктопный UI сопряжение по QR не замкнётся**: камеры нет, строку пейлоада ядро
>   наружу не отдаёт. Через шесть символов — замыкается. Ядро умеет оба пути:
>   `tests/pairing.rs` сопрягает два ядра камерой, `tests/net.rs` — руками через сеть.
>
> Сверх написанного ниже: пейлоад **подписан**, и повторное сопряжение **снимает отзыв** —
> «Сопрячь заново» из списка устройств иначе ничего бы не возвращало.

Зависит от S1. Пункт «первичный перенос записей» — от S3/S4; до них `confirm_pairing` записывает
устройство и возвращает `records_transferred: 0`, и это правда, а не заглушка.

**`get_pairing_payload` → `PairingOffer`.** TTL кода — **3 минуты** (`PAIRING_CODE_TTL_MS` в
`mock/pairing.ts`): столько нужно, чтобы дойти до второго устройства, и мало, чтобы забытым на
экране кодом кто-то воспользовался. Просроченный сеанс → `PAIRING_EXPIRED`.

**QR кодирует ядро, не UI.** Причина не в удобстве: в пейлоаде лежит одноразовый ключ сеанса, и чем
меньше он существует в виде JS-строки, тем лучше. Нужен крейт кодирования QR, отдающий модули;
наружу — `QrMatrix { size, rows }`, где `rows` — строки из `'1'`/`'0'`. Поля вокруг рисует UI.

**`manual_code`** — 6 символов алфавита `23456789ABCDEFGHJKLMNPQRSTUVWXYZ` (без `0/O/1/I/L`: код
диктуют вслух). Случайность — у ОС, через `crypto::random_bytes`. Предсказуемый код сопряжения
это право забрать копию хранилища, поэтому даже в деве он настоящий.

**Пейлоад** — префикс `syncra-pair:`, дальше код и полезная часть. Мок держит форму
`syncra-pair:<code6>.<hex32>`; в настоящем ядре внутри публичный ключ устройства и одноразовый ключ
сеанса. Если форма меняется — это правка `contract.ts` и `mock/pairing.ts` по согласованию.

**`submit_paired_key`** принимает **одну строку** и разбирает её сам: UI не знает формата и не
отличает полный пейлоад из QR от кода, набранного руками — с пробелами, точками-разделителями, в
нижнем регистре. Не код Syncra → `VALIDATION`.

**`fingerprint_words` — это и есть защита от MITM.** Считаются детерминированно из публичных ключей
**обеих** сторон (SAS) и обязаны совпасть на двух экранах. Словарь — переиспользовать
`src/generator/words.ru.txt`. Возвращаются **до** записи устройства в доверенные: иначе человек
сверяет отпечаток уже сопряжённого устройства, и сверка ничего не значит.

**`confirm_pairing` → `PairingResult`**: записать устройство в `devices`, перенести записи
**синкаемых** секций (`vaults.sync = 1`), вернуть `records_transferred` и `duration_ms`. Записи
локальных секций не уезжают даже на только что сопряжённое устройство (§4.2).

**`cancel_pairing`** — сеанс закрывается, ключ не запоминается, никаких следов в `devices`.

**Событие `device_paired`** уходит на той стороне, где код показывали: она ничего не вызывала и
узнать об успехе иначе не может.

**Тесты:** `tests/pairing.rs` — просроченный сеанс отвечает `PAIRING_EXPIRED`; мусор на входе даёт
`VALIDATION`; отпечаток одинаков с обеих сторон и меняется при подмене любого из ключей; отменённый
сеанс не оставляет устройства в `devices`.

### S3 — Транспорт и обнаружение (§5.1 · §5.6) ✅ СДЕЛАНО

> Раздел оставлен как есть — по нему читается, **почему** всё устроено так. Что получилось:
> `src/net/` (`discovery.rs` — mDNS, `wire.rs` — кадры, `handshake.rs` — ECDH и подпись,
> `channel.rs` — XChaCha20-Poly1305, `mod.rs` — узел), `Core::key_quiet` и сетевые аксессоры
> в `session.rs`, `trust::{authorized_peer, touch_last_seen, peer_public_key}`, `tests/net.rs`.
> Единственная новая зависимость — `mdns-sd`; async-рантайма не добавлено.
>
> **Чего в написанном ниже не было, а понадобилось:**
>
> - **`Core::key_quiet`** — вход за замок без отметки активности. `Core::key` отмечает её на
>   каждом проходе, и фоновые пробы отменяли бы автоблокировку: человек ушёл, а хранилище
>   открыто, потому что телефон в кармане отвечает на ping;
> - **режим `pairing` в рукопожатии** — узкое и намеренное исключение из «недоверенных не
>   пускаем». Сопряжение затем и нужно, чтобы впустить того, кого в `devices` ещё нет;
>   разрешены в нём только два запроса, и оба требуют знания кода;
> - **обязательство по коду вместо самого кода** (`pairing::code_commitment`): собеседник в
>   режиме сопряжения не подтверждён, и отдавать ему шесть символов — значит отдавать их
>   тому, кто, возможно, как раз их и подбирает;
> - **лимит попыток** `PAIRING_ATTEMPT_LIMIT = 5`: тридцать бит в LAN перебираются за
>   секунды, а длину кода увеличить нельзя — его диктуют вслух;
> - **`session_public` из пейлоада** наконец работает: показывающая сторона подписывает им
>   ECDH канала сопряжения, и прочитавший QR узнаёт тот самый экран среди соседей.
>
> **Сверх написанного ниже:** `get_sync_status` и `sync_now` стали настоящими в той части,
> которую S3 знает (живой `peers_online`, фазы `idle`/`searching`/`error`), и обе ушли за
> замок — как в фейк-ядре.

Самая архитектурно нагруженная задача. Одно решение зафиксировать до первой строчки кода:

> **Сеть не держит `Mutex<Core>`.** Ядро синхронное и живёт под мьютексом (`commands.rs::CoreState`);
> любой сетевой таймаут, взятый под этим замком, замораживает весь UI — включая кнопку «запереть».
> Сетевой слой работает в **отдельном потоке/рантайме** и трогает ядро короткими операциями через
> канал: «дай манифест», «прими дифф». Долгое ожидание всегда снаружи замка.

**Новый модуль** `src/net/` (§8.3 «Discovery» + транспорт).

**Обнаружение.** §5.1 называет ARP «предварительно»; §8.1 разрешает «ARP/mDNS». Берём **mDNS**:
ARP требует сырых сокетов и прав администратора, не даёт имени сервиса и порта, а на iOS (MVP 2)
недоступен вовсе — при том что mDNS там штатный механизм. Обоснование записать в код, чтобы к
вопросу не возвращались. Анонс и просмотр — служба вида `_syncra._tcp.local`.

**Транспорт** — собственный протокол поверх **TCP** (§5.6, ради гарантии доставки).

**Рукопожатие:** ECDH на X25519 → сессионный ключ → канал под XChaCha20-Poly1305; аутентификация
подписью Ed25519, которая проверяется по **сохранённому в `devices` публичному ключу**. Устройство,
которого нет в `devices`, и устройство с `revoked_at != null` не пускаются. Ни MAC, ни IP в решении
о доверии не участвуют (§2.1) — они только помогают найти адрес.

**События.** `device_paired` — сюда же: сторона, которая показывала код, узнаёт об успехе
только по сети, и до этого шага уведомить её нечем (см. S2). Здесь же оживает ввод кода руками:
шесть символов — это имя сеанса, а не ключ, и по ним пир ищется в LAN.
`peer_found` — про конкретное устройство (по нему двигается `last_seen_at` в списке).
`sync_status` — **полный статус**, а не дельта: подписка живёт не всё время работы окна, и
собранное по кусочкам состояние разъедется с ядром на первом же пропущенном событии.

**Тесты:** `tests/net.rs` — рукопожатие двух ядер на loopback; недоверенный ключ не проходит;
отозванное устройство не проходит; подмена подписи не проходит.

### S4 — Дифференциальный протокол синхронизации (F10, §5.3)

Ядро задачи и ядро продукта.

**Манифест.** Инициатор шлёт компактный список `{record_id, version, updated_at, deleted_at}` —
**только по секциям с `vaults.sync = 1`**. Здесь флаг наконец начинает работать. Партнёр сравнивает
со своим состоянием и отдаёт назад только то, чего у инициатора нет или что у него устарело.
Свежесть определяет **`version`**, а не время: часы на двух устройствах расходятся, счётчик — нет
(§5.2). `updated_at` едет для показа человеку.

**Секреты через границу устройств — самая легко пропускаемая деталь.** Мастер-пароли на двух
устройствах разные, значит ключи хранилищ разные, и **шифротексты копировать нельзя**. Порядок:
отправитель распечатывает секрет своим ключом → канал шифрует его на сессионный ключ (§3.2) →
получатель запечатывает **своим** ключом хранилища с правильным AAD `field_aad(record_id, field)`.
AAD привязан к записи и полю, поэтому подставить чужой шифротекст не выйдет — но и переиспользовать
чужой тоже.

**`pending_records`** требует знать, что уже уехало. Добавить учёт «последняя синхронизированная
версия» — таблица `sync_state (device_id, record_id, synced_version)` или колонка в `records`, если
хватает одной точки отсчёта. Это же значение станет **общим предком** для S5, поэтому решать надо
здесь и один раз. Записи локальных секций в `pending_records` не попадают: им некуда ехать.

**Применение диффа** — транзакцией: наполовину применённый дифф хуже, чем неприменённый.

**Надгробия** распространяются наравне с записями (§5.4), иначе удалённая запись воскреснет с
другого устройства.

**`sync_now` и автоцикл.** Автоматические попытки с паузой (макет обещает «следующая попытка через
минуту, вручную можно раньше»); `sync_now` не ждёт следующей. `SyncPhase` — машинное состояние
(`idle` / `searching` / `syncing` / `error`), шесть видов индикатора UI выводит сам. Счётчика
конфликтов в `SyncStatus` нет намеренно — он приходит из `list_conflicts`.

**Тесты:** `tests/sync.rs` — два ядра на временных БД сходятся в одинаковое состояние; локальная
секция не уезжает; надгробие переживает встречу и запись не воскресает; повторная синхронизация без
изменений не гоняет ни одной записи; после синхронизации `pending_records` пуст.

### S5 — Конфликты (F11, §5.5)

**Конфликт** = обе стороны изменили запись после общего предка. Без «последней синхронизированной
версии» из S4 конфликт неотличим от обычного обновления — поэтому S5 идёт строго после S4.

**Хранение.** Таблица `conflicts` держит приехавшую версию целиком, включая секреты,
**перешифрованные локальным ключом** (правило S4 действует и здесь). Конфликт ждёт в списке столько,
сколько нужно: немедленной реакции он не требует.

**`list_conflicts` → `RecordConflict`** с `differing_fields`. Секретные поля там есть **как имена**:
«пароли различаются» — это факт о записи, а не пароль. Значений в списке нет.

**`resolve_conflict` принимает сторону** (`local` / `remote`), а не номер версии: конфликт растёт из
общего предка, и обе стороны сплошь и рядом несут одно и то же число. Человек выбирает **колонку**,
а не цифру. Победившая версия становится обычной записью с новым `version`; проигравшая **не
склеивается** с ней по полям — §5.5 обещает выбор записи целиком.

**`get_conflict_secret`** отдаёт одно поле **обеих** сторон сразу: сравнить одно с другим — весь
смысл действия. Разово, по нажатию, по правилам `get_secret`.

**Событие `conflict_raised`.**

**Тесты:** `tests/conflicts.rs` — расхождение поднимает ровно один конфликт; `differing_fields`
перечисляет изменённые поля и не содержит значений; разрешение в любую сторону даёт запись с новым
`version` и снимает конфликт; выбранная сторона уезжает партнёру при следующей синхронизации.

### S6 — Импорт, экспорт, бэкап (F12, §6.2 · §6.3)

**От S1–S5 не зависит — можно вести параллельно с сетевой веткой.**

Главное решение всего F12: **ни CSV, ни бэкап не пересекают границу IPC**. Файл собирает и пишет
ядро, наружу уходит `ExportFile` — путь, размер, число записей, флаг `encrypted`. Иначе экспорт стал
бы четвёртой командой с открытым текстом, причём выкладывающей **все** пароли разом.

**`export_csv`** — мастер-пароль обязателен, даже если хранилище открыто: открытая программа на
своём компьютере и файл со всеми паролями открытым текстом — поступки разной цены, и второй
подтверждается отдельно. `encrypted: false`.

**`export_backup`** — контейнер под тем же мастер-паролем. Формат описать в коде подробно, его
придётся читать через год: magic-строка, версия формата, соль, параметры KDF, AEAD-полезная нагрузка.
Версия формата в файле обязательна — бэкап открывают тем ядром, которого ещё нет.

**`delete_export`** удаляет **только файлы, созданные ядром в этом сеансе**: реестр созданных путей
живёт в `Core`. Команда, которой можно передать произвольный путь, — это способ стереть с диска что
угодно чужими руками. Незнакомый путь → `NOT_FOUND`.

**`restore_backup`** — только на **неинициализированном** хранилище, иначе `ALREADY_INITIALIZED`:
восстановление поверх живого хранилища это слияние двух историй, то есть задача S4/S5, а молча
перезаписать чужие записи файлом с флешки нельзя. Пароль здесь — **от файла**; он же становится
мастер-паролем восстановленного хранилища, которое остаётся открытым.

**Выбор файла — дело оболочки.** `begin_import` и `restore_backup` возвращают `null`, когда человек
закрыл диалог, — значит диалог открывает `syncra-app` (плагин диалогов Tauri, добавление
согласовать), а в ядро приходит готовый путь. Отказ от выбора **не ошибка** и ошибкой не
показывается.

**Импорт.** Источники `chrome | firefox | 1password | bitwarden | keepass | csv`. Предпросмотр —
первые `IMPORT_PREVIEW_ROWS` (8) строк **без паролей**: показать, что попадёт внутрь, нужно, а
выкладывать на экран сотни чужих паролей — нет. Разобранные строки вместе с паролями остаются **в
ядре** до `commit_import`; `cancel_import` заставляет их забыть. `commit_import` заводит под импорт
**отдельную секцию** и удаляет исходный файл — `source_file_deleted` это флаг, а не обещание:
удалить не всегда удаётся (флешка, права), а обещание §3.10 макета должно быть проверяемым.

**Тесты:** `tests/transfer.rs` — CSV с неверным мастер-паролем не создаёт файла; бэкап
восстанавливается в идентичное хранилище; восстановление поверх живого хранилища отбивается;
`delete_export` на чужой путь отвечает `NOT_FOUND` и файл не трогает; `cancel_import` не оставляет
разобранных строк; предпросмотр не содержит ни одного пароля.

### S7 — Названные долги

Три независимых пункта, приоритизируются отдельно.

**S7.1 — Шифрование метаданных at-rest (§3.1).** Сегодня `service_name`, `login` и `urls` лежат в
файле открыто: пополевое шифрование закрывает секреты, но не их. Варианты — SQLCipher (фича
`rusqlite`; ломает `bundled` и требует отдельной сборки) либо пополевое шифрование метаданных
(ломает поиск и `ORDER BY` средствами SQL). **Решать после S4:** сетевой код тоже читает метаданные,
и переделывать хранение дважды незачем. Закрывая долг, переписать вместе с ним тест
`tests/at_rest.rs::metadata_is_deliberately_not_encrypted_in_this_step` и «границу шага» в
`README.md` — тест написан так, чтобы упасть и потребовать этого.

**S7.2 — GC надгробий, 30 дней (§5.4).** Чистка при отпирании или по расписанию. Срок жёсткий и
пользовательской настройки не имеет: это невидимый механизм, и давать от него рычаги нельзя.
Осторожно с порядком: чистить можно только то, что заведомо разошлось по сети.

**S7.3 — PIN-энролмент (F13).** Требует **расширения контракта**: команд заведения и снятия PIN там
нет вовсе (фейк-ядро заводит PIN дев-ручкой `control.enrollPin`). Порядок работ: согласование с
фронт-агентом → правка `contract.ts` → ядро. До тех пор `unlock_with_pin` и
`PinStatus.enrolled: false` остаются честным отказом, а не недоделкой.

## 5. За горизонтом MVP 1

Не начинать, пока MVP 1 не закрыт (§9 спека).

**Фаза 2 — `get_totp_code`.** Поле `totp_secret` заведено в схеме с первого дня намеренно: добавлять
новое **секретное** поле в уже синхронизируемую зашифрованную схему потом означало бы миграцию
шифрованных данных на всех устройствах. Само вычисление кода — отдельная задача. Считает его
**ядро**: через границу идёт шестизначное число, живущее секунды, а `totp_secret` остаётся внутри.
Обратный вариант — отдать фронту ключ — это криптография на JS и вечный секрет в памяти вкладки.

**MVP 2 — автозаполнение и другие платформы.** iOS-клиент, AutoFill Credential Provider (Swift,
нативно — требование Apple), браузерное расширение на десктопе. Три тонкие точки платформенной
интеграции описаны в §8.4 спека; всё остальное — этот же Rust-крейт и тот же Vue-фронт.

## 6. Как проверять

```sh
cd server
cargo test
cargo clippy --all-targets -- -D warnings
cargo fmt --all -- --check
```

Настоящий mDNS в `cargo test` не участвует: мультикаст зависит от брандмауэра и от того, что
ещё крутится в сети у запускающего. Проверяется он отдельно и руками:

```sh
cargo test -p syncra-core --test net -- --ignored --nocapture
```

Сквозной сценарий для S3–S5 нужен на **двух** экземплярах приложения с разными папками данных в
одной локальной сети:

```sh
cargo tauri dev --manifest-path crates/syncra-app/Cargo.toml
```

Фронт против настоящего ядра (а не фейк-ядра) — из `../client`, требуется Node ≥ 22.18:

```sh
npm run dev -- --mode tauri
```
