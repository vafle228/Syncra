# Syncra — Rust-ядро

Ядро и оболочка Syncra: крипта, хранилище и мост IPC к Vue-фронту из `../client`.

Источник истины по продукту — [`../syncra-spec.md`](../syncra-spec.md).
Договор с фронтом — [`../client/src/core/contract.ts`](../client/src/core/contract.ts).

## Что готово

Шаг 1: **жизненный цикл хранилища и CRUD**. Шаг 2: **генератор и безопасность**.
Шаг 3: **идентичность устройства и таблица доверия** (S1 из `FEATURE_PLAN.md`).
Шаг 4: **сопряжение по QR** (S2). Шаг 5: **обнаружение и транспорт** (S3).
Шаг 6: **дифференциальный обмен записями** (S4). Шаг 7: **разрешение
расхождений** (S5). Шаг 8: **импорт, экспорт и бэкап** (S6). Шаг 9:
**чистка надгробий по сроку** (S7.2) и **шифрование метаданных at-rest** (S7.1).

Коды подтверждения (`get_totp_code`) — фаза 2, за горизонтом MVP 1.
Эта команда **зарегистрирована** и отвечает внятным отказом: незарегистрированную команду
Tauri отвергает строкой, которую фронт показал бы как «непредвиденную ошибку ядра».

Что именно осталось и в каком порядке это писать — [`FEATURE_PLAN.md`](FEATURE_PLAN.md):
разбор разрыва «спека ↔ ядро» и задачи S1–S7 до конца MVP 1.

**Автоблокировку считает ядро**, а не фронт: срок берётся из настроек, отсчёт бездействия
идёт по проходам за замок, а оболочка раз в секунду спрашивает ядро и при срабатывании
шлёт `locked` с `reason: 'timeout'`. Своего таймера у фронта быть не должно — два таймера
дают две правды о том, заперто ли хранилище.

> **Граница шага по PIN:** завести PIN нечем — команды энролмента в контракте нет
> (фейк-ядро заводит его ручкой `control.enrollPin` для дева). `unlock_with_pin` поэтому
> проверяет форму запроса и честно отвечает «быстрый вход не настроен», а
> `VaultStatus.pin.enrolled` — `false`. Экран блокировки по нему и решает не показывать
> клавиатуру.

### Смена мастер-пароля

`change_master_password` перешифровывает хранилище целиком: новая соль, новый ключ, новый
верификатор и все секретные поля заново — одной транзакцией, потому что наполовину
перешифрованное хранилище не открывается ни старым паролем, ни новым.

`version`, `updated_at` и `password_updated_at` записей при этом **не меняются**: смена
ключа — не правка записи, и поднимать версии значило бы наплодить расхождений для будущей
синхронизации на ровном месте (§5.2).

В той же транзакции перешифровывается **приватный ключ устройства**: он защищён ключом
хранилища наравне с паролями, и не тронуть его значило бы терять идентичность устройства
при каждой смене пароля — а заметить это удалось бы только в сети и только через неделю.

### Идентичность устройства и доверие

При создании хранилища устройство заводит **долговременную пару ключей**: Ed25519 для
подписи и X25519 для обмена ключами (§2.1, §8.1). Приватная половина лежит в `meta`
запечатанной **ключом хранилища** — то есть под мастер-паролем, ровно как пароли: украденный
файл не даёт права представляться этим устройством. Публичная половина лежит открыто, в
строке таблицы `devices`, и именно она — корень доверия. Ни MAC, ни IP в решении о доверии
не участвуют: они помогают найти адрес, но подделываются (§2.1).

Отпечаток — четыре слова из того же словаря, что у генератора, посчитанные детерминированно
из публичных ключей. В сопряжении в счёт идут ключи **обеих** сторон, отсортированные: порядок
сторон не определён — одно устройство читает код другого, — и без сортировки два экрана
показали бы разные слова.

Отзыв (§2.3) идемпотентен и `revoked_at` не переписывает: момент отзыва — факт, а не текущее
значение. Себя отозвать нельзя — устройство в руках единственное, что у человека точно есть.
Отозванные из списка **не исчезают**: человек должен видеть, что ноутбук отозван, а не что
его не было. Повторное сопряжение того же устройства отзыв **снимает**: вернуть отозванный
ноутбук можно только новым сопряжением, и раз оно состоялось — человек его подтвердил.

### Сопряжение по QR

Код кодирует **ядро**, а не UI: в пейлоаде лежат публичный ключ устройства и одноразовый ключ
сеанса, и чем меньше они существуют в виде JS-строки, тем лучше. Наружу уходит `QrMatrix` —
`size` строк по `size` символов `'1'`/`'0'`; поля вокруг рисует UI.

Пейлоад — `SYNCRA-PAIR:<КОД6>.<base32>`. Прописные и base32 не для красоты: алфавит QR
(`alphanumeric mode`) не знает строчных букв, и одна такая буква переводит весь код в
побайтовый режим, заметно раздувая картинку. Внутри — версия формата, тип и имя устройства,
публичный ключ (`ed25519 || x25519`), одноразовый ключ сеанса и **подпись Ed25519** над всем
этим вместе с кодом. Подпись доказывает, что код нарисовал держатель приватного ключа и что
его не переписали по дороге; проверяется она ключом из самого пейлоада — этого довольно,
потому что QR и есть тот внеполосный доверенный канал, ради которого сопряжение затевалось
(§2.2). Разбирает всё это ядро: `submit_paired_key` принимает **одну строку** и не требует от
UI знать формат — в том числе код, набранный руками, с пробелами и в нижнем регистре.

Код живёт три минуты, каждый запрос выдаёт новый, а прежний перестаёт годиться сразу —
одноразовый ключ на то и одноразовый. Отпечаток возвращается **до** записи устройства в
доверенные: иначе человек сверял бы слова уже сопряжённого устройства, и сверка не значила бы
ничего. Замок стирает и показанный код, и начатые сеансы: тот, кто прочитал код, получает
право забрать копию хранилища, и переживать блокировку такому праву незачем.

> **Граница шага:** через десктопный UI сопряжение по QR не замкнётся. Камеры на десктопе
> нет, а строку пейлоада ядро наружу не отдаёт — значит человеку на экране доступны только
> шесть символов, и работают они через поиск в сети (ниже). Ядро при этом умеет оба пути:
> `tests/pairing.rs` сопрягает два ядра, обмениваясь кодами так, как их перенесла бы камера,
> а `tests/net.rs` — так, как их набирают руками.

## Сеть: обнаружение и транспорт

Синхронизация работает **только в пределах одной локальной сети** (§5.1). Устройства находят
друг друга по **mDNS** (служба `_syncra._tcp.local`), разговаривают по **TCP** собственным
протоколом (§5.6). Почему mDNS, а не ARP, расписано в шапке `src/net/discovery.rs`: ARP требует
сырых сокетов и прав администратора, не несёт ни имени службы, ни порта, а на iOS (MVP 2)
недоступен вовсе.

**В анонсе нет идентичности.** Имя экземпляра — случайный токен, новый на каждое отпирание;
в TXT только версия. Ни `device_id`, ни ключа: mDNS слушает вся сеть, стабильный идентификатор
в широковещании даёт следить за устройством и при этом ничего не доказывает — назваться чужим
`device_id` может кто угодно. Кто перед нами, выясняет рукопожатие, и только оно.

**Рукопожатие.** Эфемерный ECDH на X25519 даёт общий секрет, из него выводятся два ключа
канала — свой на каждое направление, — и уже внутри канала каждая сторона подписывает
транскрипт разговора долговременным ключом Ed25519. Подпись проверяется по публичному ключу
**из `devices`**: устройства, которого там нет, и устройства с `revoked_at != null` не
пускают. Ни MAC, ни IP в решении о доверии не участвуют (§2.1). Канал — XChaCha20-Poly1305,
кадр за кадром, со счётчиком nonce на каждое направление.

**Сеть не держит `Mutex<Core>`.** Ядро синхронное и живёт под мьютексом; сетевой таймаут,
взятый под этим замком, заморозил бы весь UI, включая кнопку «Запереть». Поэтому сеть живёт в
своих потоках, ходит в ядро короткими операциями через один-единственный хелпер
(`net::Context::with_core`) и держит ядро через `Weak`. Команды, которым нужна сеть
(`submit_paired_key`, `confirm_pairing`, `get_sync_status`, `sync_now`), идут через
`net::Node`, а не через `core!`: узел умеет отпустить замок на время ожидания.

Ходит сеть за замок **не отмечая активность** (`Core::key_quiet`). Иначе фоновый обмен с
телефоном в кармане отменял бы автоблокировку: человек ушёл от компьютера, а хранилище стоит
открытым, потому что сосед исправно отвечает на ping.

**Сеть поднимается и опускается сторожем**, тем же, что считает автоблокировку: отпертому
хранилищу она нужна, запертому — нет. Вызвать это из `Core::unlock` нельзя — там уже взят
мьютекс, а сети он нужен, чтобы прочитать ключи.

**Шесть символов** — имя сеанса, а не ключ: по ним устройство ищут среди соседей. Сам код в
сеть не уходит никогда — едет обязательство `SHA-256(домен ‖ транскрипт ‖ код)`, привязанное к
конкретному соединению. Тридцать бит перебираются в LAN за секунды, поэтому защита не в длине
кода: после **пяти** промахов оффер сгорает, а слова отпечатка человек всё равно сверяет
глазами. Сторона, показавшая код, узнаёт об успехе событием `device_paired` — она ничего не
вызывала, и рассказать ей больше нечем.

> Доставка `device_paired` идёт по сети и может не дойти (сосед успел уснуть, сеть моргнула).
> Тогда прочитавшая сторона сопряжена, а показавшая про неё не знает: человек увидит это в
> списке устройств и покажет код заново. Обещать доставку в ответе команды нельзя — команда
> уже ответила.

## Обмен записями

Дифференциальный (§5.3): инициатор шлёт **манифест** — по строке на запись, `{record_id,
vault_id, version, updated_at, deleted_at}` плюс флаг «уезжает ли она отсюда», — а собеседник
сравнивает его со своим состоянием и отвечает, что хочет получить. Второй манифест по проводу
не едет: обе стороны считают по одному и тому же правилу, поэтому «что я пошлю» у одной
совпадает с «что я попрошу» у другой.

**Свежесть решает `version`, а не время** (§5.2). Часы на двух устройствах расходятся, счётчик
— нет; `updated_at` едет рядом, но только чтобы показать его человеку. Ровно одна функция
(`sync::classify`) решает судьбу приехавшей версии — и решает её по **трём** числам, а не по
двум: третье это общий предок, см. «Расхождения» ниже.

**Шифротексты не копируются.** Мастер-пароли на двух устройствах разные, значит разные и ключи
хранилищ. Отправитель распечатывает секрет своим ключом, канал шифрует его на сессионный (§3.2),
получатель запечатывает **своим** с тем же AAD `record_id + имя поля`. Открытый текст живёт
только внутри процесса, границу IPC не пересекает, и четвёртой команды Закона №1 не появилось.
`Debug` у записи на проводе написан руками и печатает `<скрыт>`: производный вывалил бы пароль
в первый же лог.

**Надгробия ездят наравне с записями** (§5.4): не поехавшее удаление воскресает с другого
устройства, а это худшая поломка, какая бывает у менеджера паролей.

**Секция едет вместе с записью.** `vault_id` у сторон один и тот же, а имя и цвет нужны, чтобы
приехавшая запись легла в узнаваемую папку. Незнакомая секция заводится синкаемой; выключенная
(`sync = 0`) не уезжает **и не приезжает** — §4.2 действует в обе стороны. Строки локальных
секций в манифесте при этом есть, помеченные «не поедет»: без них собеседник видел бы только
«у него этой записи нет» и слал бы её заново каждую минуту.

**Порциями.** Кадр ограничен мегабайтом, и потолок опустить нельзя — длину кадра называет
сторона на том конце. Хранилище на тысячу записей в один кадр не влезает, поэтому и манифест,
и дифф режутся на части, а `last` закрывает поток.

**Круг ведёт инициатор.** Отвечающая сторона — это цикл «принял кадр → ответил кадром»: два
кадра подряд в одну сторону были бы или дедлоком, или рассинхроном счётчика nonce. Оба
устройства ходят друг к другу сами, поэтому встречные круги неизбежны; кто первый занял право
вести, тот и ведёт, а второй получает `SyncBusy` и расходится молча. Обрыв связи вместо этого
зажигал бы «обмен не удался» там, где всё в порядке.

**Автоцикл — раз в минуту**, `sync_now` не ждёт своей минуты. Ответ команды круга при этом не
ждёт: обмен идёт по сети, а команда должна вернуться сразу — чем он кончился, расскажет
событие `sync_status`.

**«Ждут отправки» считается по пирам.** Запись попадает в `pending_records`, только если есть
действующее сопряжённое устройство, которому она ещё не уехала. Нет таких устройств — список
пуст, и индикатор спокойно говорит «рядом никого» вместо жёлтого «изменения ждут отправки».

> **Расхождение с фейк-ядром, осознанное.** `mock/index.ts::markPending` про устройства не
> знает вовсе и помечает ждущей любую правку. Обоснование отступления — формулировка самого
> контракта, которой он исключает из этого списка локальные секции: «им некуда ехать» (§4.2).
> Одинокое устройство иначе вечно показывало бы жёлтое «изменения ждут отправки», хотя ждать
> их некому. Отметить во фронтовом `TASKS.md`.

**Первичный перенос при сопряжении.** `confirm_pairing` доставляет соседу «я тебя записал»
первым проходом синхронно и тем же заходом гоняет круг обмена — `records_transferred` в ответе
настоящий. Не достучались с первого раза: сопряжение всё равно состоялось, ноль честный, а
доставку и перенос доделывает фон.

> **Граница шага:** сторона, которая ПОКАЗЫВАЛА код, отдаёт в `device_paired`
> `records_transferred: 0`. Это не заглушка: адреса слушателя соседа она не знает — в сокете
> сопряжения его эфемерный клиентский порт, — и позвонить ему до первой пробы некуда. Записи
> приезжают через секунды, ближайшим кругом, и видно это по `sync_status`.

**Надгробия живут 30 дней — и не по календарю одному** (§5.4). Стереть надгробие насовсем
можно только тогда, когда воскресать записи неоткуда, поэтому условий два и оба обязательны:
прошёл срок **и** каждое действующее доверенное устройство отчиталось, что довезло эту версию
(`sync_state`). Соседей нет вовсе — второе условие выполнено пустым множеством: воскрешать
некому. Отозванный сосед не считается, ему больше ничего не поедет ни в ту, ни в другую
сторону (§2.3). Чистит `sync::tombstones` — при отпирании и в конце успешного круга обмена:
первое ловит хранилище, неделями не выходившее в сеть, второе — единственный момент, когда
про надгробие впервые становится известно, что оно разошлось.

> **Названная обратная сторона:** надгробие для устройства, которое **не появляется**, не
> чистится никогда. Это выбор в пользу человека — строка в БД против воскресшего пароля, — и
> снимается он отзывом устройства, то есть тем же действием, которым человек и так признаёт,
> что ноутбук не вернётся. Срок при этом жёсткий и пользовательской настройки не имеет
> намеренно: это невидимый механизм, а рычаг от невидимого механизма — способ молча испортить
> себе хранилище.
>
> Отказ чистки **проглатывается** — единственное такое место в ядре. Уборку человек не
> заказывал и результата её не увидит; запереть его снаружи собственного хранилища из-за
> неудавшегося `DELETE` было бы обменом важного на неважное. Не прошло сейчас — пройдёт при
> следующем отпирании.

## Расхождения

**Конфликт — это факт о предке, а не о числах** (§5.5). «Версия 5 против версии 5» само по
себе не значит ничего: обе стороны могли прийти к пятёрке одной и той же правкой. Спор
начинается там, где обе ушли от общей точки — от `sync_state.synced_version`, той самой
отметки, которую завёл S4. Решает это одна функция, `sync::classify`, и решает по трём
числам: приехавшая версия, местная и предок.

**Нет предка — нет и спора.** Отметки стираются при отзыве и при (повторном) сопряжении, и
вернувшийся ноутбук получает хранилище заново. Считать расхождением каждую его запись
значило бы встречать человека сотней конфликтов там, где на деле просто новое знакомство.
Тогда работает прежнее правило: больше версия — та и права.

**Одинаковое содержимое — не спор.** Прежде чем звать человека, ядро сравнивает стороны
целиком, включая распечатанные секреты. Совпало — значит счётчики разошлись, а данные нет,
и решать тут нечего.

**Спор живёт на одной стороне** — на той, куда приехала чужая версия. Отправитель свою
правку доставил и двигает отметку («он её видел»); получатель отметку **не** двигает, иначе
следующий круг увидел бы «сошлись» и расхождение исчезло бы из виду навсегда. По той же
причине спорные записи вычитаются из `settled`: объявить предком текущую версию — то же
самое, что стереть спор.

**Разрешение двигает предка** до версии соседа: «я её видел и учёл». Без этого следующий же
круг поднял бы тот же конфликт — победившая версия больше предка, чужая тоже. С ним выбор
человека уезжает соседу обычной записью и принимается там молча. Выбирать дважды, на двух
устройствах, не приходится — это проверяет
`tests/conflicts.rs::a_resolved_side_travels_and_does_not_raise_a_second_dispute`.

**Победившая версия получает `max(местная, приехавшая) + 1`.** Не «местная + 1»: с ним
проигравшая вернулась бы следующим кругом как более свежая, и человек выбирал бы заново до
бесконечности. Проигравшая при этом **не склеивается** с победившей по полям — §5.5 обещает
выбор записи целиком.

**Местная сторона в списке — живая запись, а не снимок.** Пока спор ждёт, запись можно
править, и показывать человеку устаревший вариант его же данных было бы враньём. Заморожен
ровно один момент — `raised_at`.

**Секретов в списке нет, имена полей есть.** `differing_fields` говорит «пароли
различаются» — это факт о записи, а не пароль. Сравнение идёт внутри ядра; наружу значения
отдаёт единственная команда `get_conflict_secret`, разово и обе стороны сразу: сравнить одно
с другим — весь смысл действия. Это вторая из трёх команд Закона №1, и обращение с ней такое
же, как с `get_secret`.

> **Расхождение с фейк-ядром, осознанное.** `mock/index.ts::control.raiseConflict` кладёт
> спор безусловно — ему и нечем решать иначе, сети под ним нет. Настоящее ядро поднимает
> конфликт только при известном общем предке и только при разном содержимом: это не другая
> трактовка §5.5, а то самое «обе стороны изменили запись после общего предка», которое в
> моке изобразить было нечем. Всё, что фронт видит на экране разрешения, — форма
> `RecordConflict`, порядок `differing_fields`, правила `resolve_conflict` — совпадает с
> моком дословно и проверено `tests/wire.rs` и `tests/conflicts.rs`.

> **Граница шага: надгробие в споре не участвует.** Если одна из сторон — удаление, конфликт
> не поднимается: удаление побеждает. Причина в типе — `ConflictVersion` (`contract.ts:854`)
> не умеет сказать «эта сторона удалена», а показывать нечего и по существу: секреты у
> надгробия стёрты. Менять это — правка контракта, а не трактовка. §5.4 при этом остаётся в
> силе, причём усиленным: не поехавшее удаление воскресает, и это худшая поломка, какая
> бывает у менеджера паролей.

## Перенос данных

Экспорт, импорт и бэкап (F12, §6.2) устроены вокруг одного решения: **ни CSV, ни бэкап не
пересекают границу IPC**. Файл целиком собирает и пишет ядро, наружу уходит `ExportFile` —
путь, размер, число записей. Иначе экспорт стал бы четвёртой командой Закона №1, причём
отдающей не одно поле по нажатию, а **все** пароли разом, одной строкой в куче JS.

Импорт устроен зеркально: разобранные чужие пароли живут **в ядре** до `commit_import`, а
наружу идёт предпросмотр — сайт, логин и что со строкой будет. Пароля в строке предпросмотра
нет и быть не может: показать, что попадёт внутрь, нужно, а выкладывать на экран сотни чужих
паролей — нет.

**Куда класть файл и какой выбрать — дело оболочки.** Папку загрузок называет `syncra-app`,
системное окно выбора файла открывает тоже она (`tauri-plugin-dialog`, единственный плагин в
сборке, и зовётся он **только** из Rust). Ядро про платформу не знает: путь приходит к нему
готовым аргументом, как и путь к БД. «Человек закрыл окно выбора» до ядра не доходит вовсе —
`null` рождает оболочка, которая в таком случае просто не зовёт ядро.

**Мьютекс ядра на время диалога не берётся.** Модальное окно живёт столько, сколько человек
думает; взятый на это время замок заморозил бы весь UI, включая кнопку «Запереть» — тот же
закон, по которому сеть не держит `Mutex<Core>`.

### CSV — файл для переезда

Мастер-пароль обязателен, даже когда хранилище открыто: открытая программа на своём
компьютере и файл со всеми паролями открытым текстом — поступки разной цены, и второй
подтверждается отдельно. Уезжают **все живые записи**, включая локальные секции: это переезд,
а не синхронизация, и §4.2 здесь ни при чём.

Формат — диалект Chrome (`name,url,username,password,note`) плюс шестая колонка `totp`:
молча потерять при переезде ключи подтверждения хуже, чем дать чужому импортёру лишний
столбец, который он пропустит. У записи Syncra бывает до шестнадцати адресов, а в диалекте
один — остальные дописываются в заметку, чтобы экспорт был без потерь.

`encrypted: false`, и UI обязан продолжать говорить об этом **после** экспорта, а не только
до него. Повторный экспорт в тот же день перезаписывает файл, а не плодит второй.

### Бэкап — резервная копия

Формат подробно описан в шапке `src/transfer/backup.rs`: magic, версия формата, идентификатор
и параметры KDF, соль, дальше полезная нагрузка под XChaCha20-Poly1305. Версия лежит **в
файле**: бэкап открывают тем ядром, которого ещё нет.

**AAD полезной нагрузки — весь заголовок целиком.** Без этого в чужом файле можно было бы
понизить параметры KDF и заставить чужое ядро считать ключ по слабым — а получатель не
заметил бы ничего, потому что пароль-то подошёл бы.

В файл не едут **надгробия** (бэкап — снимок, а не история; секретов у надгробия нет) и
**пара ключей устройства с таблицей `devices`**: §6.3 говорит про «все устройства потеряны», а
перенести идентичность в файл значило бы дать двум машинам право представляться одним
устройством. Восстановленное хранилище заводит **новую** пару и сопрягается заново.

`restore_backup` работает только на устройстве **без** хранилища: восстановление поверх живого
— это слияние двух историй, то есть задача S4/S5, а молча перезаписать чужие записи файлом с
флешки нельзя. Пароль здесь — от **файла**, и он же становится мастер-паролем восстановленного
хранилища; соль при этом новая, потому что соль из файла означала бы, что укравший бэкап уже
посчитал половину работы по подбору. Секции и записи переезжают со своими идентификаторами,
версиями и датами: это то же самое хранилище, а не его копия с новой историей (§5.2).

### Импорт

Колонки ищутся по **именам** заголовка, а не по номерам: Chrome, Firefox, 1Password и KeePass
раскладывают одни и те же пять полей в разном порядке, а Firefox не отдаёт имени сервиса вовсе
— оно достаётся из адреса. Bitwarden понимается и как JSON, и как CSV: что именно принёс
человек, видно по первому непробельному символу файла, а не по названному источнику.

Дубликат считается **по адресу и логину** (§4.4), а не по имени сервиса: имя не уникально.
Пары «известных» снимаются один раз до прохода по файлу — дубликаты внутри самого файла между
собой не схлопываются, потому что два аккаунта на один сервис это норма, а не коллизия.

Строка без пароля записью не становится: заведённый пустой пароль молча притворился бы
рабочим. В `skipped` она при этом не идёт — пропускать было нечего; там только дубликаты, и
только когда об этом просили.

Всё ложится в **отдельную секцию** `Импорт DD.MM` (§3.10 макета: «разберёте потом, не смешивая
с текущим»); второй импорт в тот же день ложится туда же. `source_file_deleted` — настоящий
результат удаления, а не вежливость: удалить не всегда удаётся (флешка, права), и обещание
должно быть проверяемым.

Метаданные из чужого файла **приводятся, а не валидируются** — как имя секции, приехавшей от
соседа: слишком длинное поле подрезается. Пароль длиннее потолка делает строку строкой «без
пароля»: записи с обрезанным паролем быть не может.

> **Граница шага: KeePass `.kdbx` не читается.** База KeePass всегда зашифрована, а
> `begin_import` в контракте (`contract.ts:1092`) **не принимает пароля** — спросить его негде.
> Ядро отвечает `VALIDATION` с готовым лечением: «экспортируйте из KeePass CSV». То же и с
> зашифрованным экспортом Bitwarden. XML KeePass не читается по другой причине: XML-разбора в
> ядре нет, а заводить его ради одного источника дороже, чем сказать правду. Снять эту границу
> = расширить контракт полем пароля, а это правка `contract.ts` по согласованию с фронтом.
>
> **Ручного сопоставления колонок нет.** Источник «Любой CSV» обещает на экране разметить
> столбцы руками, но на проводе для этого нет ни поля в запросе, ни команды: ядро ищет колонки
> по именам заголовка. Незнакомая таблица честно отвечает «не удалось понять, где здесь
> пароли», а не заводит записи наугад.

## Как устроено хранилище

- SQLite (`rusqlite`, bundled). Файл — `syncra.db` в папке данных приложения.
- Схема версионирована: номер лежит в `meta`, миграции применяются **цепочкой** от
  записанной версии к текущей. Хранилище схемы 1 доезжает до схемы 2 при открытии, а
  пары ключей ему заводит первое же отпирание — раньше её нечем запечатать.
- Обе ссылки на `records` (`sync_state`, `conflicts`) стоят с `ON DELETE CASCADE`:
  надгробие исчезает вместе со своими отметками обмена и отложенным спором, и сиротам
  взяться неоткуда.
- Секреты (`password`, `notes`, `totp_secret`) шифруются **по полям**:
  XChaCha20-Poly1305, ключ выводится из мастер-пароля через Argon2id.
- AAD каждого поля включает `record_id` и имя поля — шифротекст нельзя
  переставить в другую запись или на место другого поля.
- Метаданные записи (`service_name`, `urls`, `login`, `account_label`) шифруются
  **одним блобом** `meta_ct` — их читают и пишут всегда вместе.
- Пространств AAD **пять**, и они взаимно непереставляемы: поле записи, поле спора,
  метаданные записи, метаданные спора, секрет устройства. Держит это
  `crypto.rs::every_aad_space_is_a_space_of_its_own`.
- Мастер-пароль проверяется распечаткой контрольного значения; отдельного хеша
  пароля в файле нет.
- Приватный ключ устройства лежит строкой в `meta`, запечатанный ключом хранилища под
  собственным AAD (`syncra:device:secret`): его нельзя выдать за пароль записи и наоборот.
- Доверенные устройства — таблица `devices`: публичный ключ, отпечаток словами, даты
  сопряжения, последней связи и отзыва. Строка при отзыве не удаляется.
- Сеанс сопряжения в файл **не попадает**: показанный код, прочитанные пейлоады и счётчик
  промахов живут в памяти `Core` и умирают вместе с замком. Схема под сопряжение не менялась.
- Сеть ничего не пишет в файл, кроме `devices.last_seen_at` и отметок обмена: адреса,
  найденные пиры и ключи соединений живут в памяти узла и умирают вместе с замком.
- Отметки обмена — таблица `sync_state`: на какой версии каждой записи хранилище сошлось
  с каждым устройством. Таблица, а не колонка в `records`: запись бывает довезена до
  ноутбука и не довезена до телефона, и одной точкой отсчёта эти два факта не описать.
  Отзыв и повторное сопряжение отметки для устройства **стирают** — вернувшийся ноутбук
  получает хранилище заново.
- Ждущие расхождения — таблица `conflicts`: приехавшая версия целиком, по строке на
  запись. Секреты в ней перешифрованы местным ключом и лежат под **своим** AAD
  (`syncra:conflict:…`), а не под обычным: с общим AAD шифротекст из `conflicts` и
  шифротекст из `records` стали бы взаимозаменяемы, и тот, кто может писать в файл,
  подставил бы приехавший пароль на место настоящего. Смена мастер-пароля перешифровывает
  и эту таблицу — в той же транзакции, что и записи с ключом устройства.
- Реестр созданных экспортов и разобранные файлы импорта в файл **не попадают**: и то, и
  другое живёт в памяти `Core`. Сеансы импорта умирают вместе с замком — там лежат чужие
  пароли открытым текстом; реестр экспортов замок переживает, потому что стереть файл с
  диска замок не умеет, а делать вид, что умеет, не будет.
- Профиль генератора и настройки безопасности лежат строками в `meta` открытым
  JSON: это настройки, а не секреты, и отдельной таблицы они не стоят. Хранилище
  без этих строк открывается умолчаниями, миграции для них не нужно.

**Метаданные тоже зашифрованы** (S7.1, §3.1). `service_name`, `urls`, `login` и `account_label`
лежат одним запечатанным блобом `meta_ct` — своё пространство AAD, отдельное и от секретов
записи, и от отложенной версии спора. Из `syncra.db` больше не вычитать, к каким сервисам
заведены пароли; надгробие свои метаданные тоже держит при себе. Держат это обещание тесты в
`tests/at_rest.rs`.

> **Почему пополе, а не SQLCipher.** Фича `sqlcipher` у `rusqlite` несовместима с `bundled` и
> требует системного `libsqlcipher` с OpenSSL — то есть внешнюю зависимость сборки на каждой
> машине, при том что весь остальной проект собирается одним `cargo build`. Платить за at-rest
> ценой «у половины разработчиков не собирается» нельзя. Подробный разбор — в шапке
> `src/storage/metadata.rs`.
>
> **Чем за это заплачено.** `WHERE service_name LIKE …` и `ORDER BY login` больше не
> существуют: поиск и сортировка идут в Rust, по расшифрованному списку. Сегодня это ничего не
> стоит (`records::list` и так сортировал в Rust, поиск живёт на фронте), на десятках тысяч
> записей будет стоить. Заодно `list_records` теперь требует ключ — читать список за замком
> больше нельзя. Длина шифротекста по-прежнему выдаёт длину метаданных: выравнивания нет ни
> здесь, ни у секретов.
>
> **Граница шага:** имена секций (`vaults.name`) и имена устройств (`devices.name`) остаются
> открытыми. «Работа» в списке секций говорит наблюдателю несравнимо меньше, чем список
> сервисов, а ключ понадобился бы половине запросов, которые сегодня обходятся без него —
> включая `vaults::adopt` внутри чужого круга обмена.
>
> **Хранилище прошлой схемы** доезжает в два приёма: миграция 6 заводит колонку под шифротекст
> (ключа при открытии файла ещё нет), а перекладка и удаление открытых колонок происходят при
> первом же отпирании — `schema::seal_legacy_metadata`, того же рода доводка, что и
> досоздание пары ключей у схемы 1. Открытые колонки именно **удаляются**: колонка, которую
> забыли перестать заполнять, — это тихий возврат к открытому тексту через полгода.

## Требования к машине

- Rust stable (`rustup`), таргет `x86_64-pc-windows-msvc`.
- Локальная сеть: при первом запуске Windows спросит разрешение брандмауэра — ядро открывает
  слушающий TCP-порт и анонсирует себя по mDNS. Без разрешения соседей не будет, а всё
  остальное продолжит работать: индикатор честно покажет «рядом никого».
- **MSVC Build Tools** (VS 2022, workload «Desktop development with C++») — нужны
  и для bundled SQLite, и для Tauri.
- WebView2 — есть в составе Windows 11.
- Для дев-петли: **Node ≥ 22.18** (требование `../client/package.json`).

## Команды

```sh
cargo test                                  # ядро целиком, без окна
cargo clippy --all-targets -- -D warnings
cargo fmt --all -- --check

cargo tauri dev    --manifest-path crates/syncra-app/Cargo.toml   # окно + дев-сервер клиента
cargo tauri build  --manifest-path crates/syncra-app/Cargo.toml   # сборка против client/dist
```

`cargo tauri` ставится отдельно: `cargo install tauri-cli --version "^2"`.

Собирать обычным `cargo build` тоже можно, но фичу `custom-protocol` тогда
нужно передать руками — `cargo tauri build` добавляет её сам:

```sh
cargo build --release -p syncra-app --features custom-protocol
```

Без неё `generate_context!` не встраивает `client/dist` в бинарник и окно
открывается на `devUrl` — пустым, если рядом не поднят Vite.

### Мок или настоящее ядро

Переключатель живёт во фронте (`client/src/core/ipc.ts`, `resolveCoreMode()`):

- `npm run dev` — против мок-ядра (по умолчанию в деве);
- `npm run dev -- --mode tauri` — против этого ядра (через `client/.env.tauri`);
  ровно это и запускает `cargo tauri dev`;
- прод-сборка всегда идёт против настоящего ядра.

## Правила

- **Закон №1:** секреты не покидают ядро иначе как по явному действию человека.
  Открытый текст отдают ровно три команды: `get_secret`, `get_conflict_secret` и
  `generate_passwords` (последняя возвращает ещё ничей пароль — но обращение с ним
  такое же). Их и после F12 три. Четвёртой не становится ни строка пейлоада
  сопряжения — наружу уходит матрица QR, — ни экспорт: файл собирает и пишет
  ядро, а наружу уходит путь к нему.
- Сообщения ошибок уходят прямо в UI: ни путей к хранилищу, ни ключей, ни
  текста ошибок SQLite в них быть не должно (`src/error.rs`).
- Поведение сверяется с фейк-ядром `../client/src/core/mock/index.ts`.
  Расхождение с ним — баг ядра, а не «другая трактовка».
