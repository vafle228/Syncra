# TASKS — Syncra Frontend (MVP 1)

План работ по фронтенд-части. Задачи — **вертикальные срезы в порядке зависимостей**. Всё делается против **мок-ядра** (см. `CLAUDE.md`), поэтому фронт не заблокирован готовностью Rust-ядра.

**Правила ведения:**
- Одна задача за раз. Не начинать следующую, пока текущая не прошла Definition of Done (`CLAUDE.md`).
- Каждая задача, трогающая границу с ядром, фиксирует нужные ей команды/события в `src/core/contract.ts`.
- Имена IPC-команд ниже — **предложение для затравки контракта**; финализируются вместе с бэкенд-агентом.
- Статусы: `[ ]` todo · `[~]` в работе · `[x]` готово.

## F1. IPC-слой + мок-ядро `[x]`
**Цель:** договор с бэком и фейк-ядро, разблокирующие всю дальнейшую UI-работу. **Самая важная задача — делать тщательно.**
- `src/core/contract.ts`: типы команд/событий (для начала unlock + records CRUD + reveal; дополняется по ходу).
- `src/core/ipc.ts`: типизированный клиент. В деве резолвится в мок, в проде — в реальный Tauri `invoke`.
- `src/core/mock/`: in-memory фейк-ядро — держит записи, эмулирует reveal, задержки, ошибки; сид-данные для разработки.
**Готово, когда:** компонент вызывает `ipc.listRecords()` и получает мок-данные; переключение мок ↔ реальный — одной точкой.
**IPC:** `unlock`, `listRecords`, `getSecret(record_id)`, `createRecord`, `updateRecord`, `deleteRecord`.

**Зафиксировано в контракте (нужно подтверждение бэкенд-агента):**
- Имена команд на проводе — **snake_case**: `unlock`, `lock`, `list_records`, `get_secret`,
  `create_record`, `update_record`, `delete_record` (`COMMAND_NAMES` в `contract.ts`).
- Каждая команда принимает **один аргумент** `request`: `invoke('list_records', { request })`.
  Поля запросов/ответов — snake_case, даты — ISO-8601 UTC.
- Ошибка ядра — `{ code, message }`, коды в `CORE_ERROR_CODES`; UI нормализует всё в `CoreError`.
  `message` показывается пользователю → не должен содержать секретов и путей.
- События: `unlocked`, `locked` (`{ locked_at, reason: manual|timeout|system }`). Остальные — по мере задач.
- Секреты пересекают границу **только** в ответе `get_secret`. `list_records` возвращает
  `RecordMeta` без секретных полей — проверяется тестом.
- Переключение реализаций: `VITE_CORE=mock|tauri`, по умолчанию прод → Tauri, дев/тесты → мок
  (`resolveCoreMode` + `initCoreClient` в `src/core/ipc.ts`, вызывается из `main.ts`).
- Мастер-пароль дев-мока: `syncra-dev` (`MOCK_MASTER_PASSWORD`).

## F3. Разблокировка / инициализация `[x]`
**Цель:** вход в приложение.
- Экран ввода мастер-пароля (универсальный фолбэк) + состояние «заблокировано / разблокировано».
- Экран первичной инициализации хранилища (UI шлёт команду init/генерации ключей — сама генерация в ядре).
- Плейсхолдеры под биометрию/PIN (реализация платформенная, glue в MVP 2).
**Готово, когда:** мок принимает/отклоняет мастер-пароль, приложение переходит в разблокированное состояние.
**IPC:** `initVault`, `unlock`, события `locked` / `unlocked`.

**Как сделано:**
- Экраны: `UnlockView.vue` (§3.8) и `SetupView.vue` (§3.9, три шага: модель без сервера →
  мастер-пароль → «хранилище создано»). PIN и биометрия — явные плейсхолдеры «в следующей
  версии», а не притворяющиеся рабочими элементы. Ветка «уже есть Syncra» ждёт F8 (pairing).
- Стор `useVaultStore`: `unknown | uninitialized | locked | unlocked`, подписка на события
  ядра (`locked` по таймауту/сну тоже закрывает UI). Мастер-пароль проходит **транзитом**
  и в состояние не попадает — проверяется тестом на `$state`.
- Навигация: один хранитель в `src/router/index.ts` (`routeForStatus`) — «объехать» замок
  ссылкой или back нельзя. Ошибка запроса статуса трактуется как «закрыто».

**Дополнено в контракте (нужно подтверждение бэкенд-агента):**
- Новые команды: `get_vault_status` → `{ initialized, unlocked, unlocked_at }` (работает на
  заблокированном и неинициализированном хранилище) и `init_vault` `{ master_password }` →
  `{ initialized_at, unlocked_at }`. Успешный `init_vault` **сразу оставляет хранилище
  разблокированным** и шлёт событие `unlocked`.
- Новый код ошибки `ALREADY_INITIALIZED` — `init_vault` по уже созданному хранилищу.
- `unlock` и все команды данных на неинициализированном хранилище отвечают `NOT_INITIALIZED`
  (а не `LOCKED`) — UI по этому отличает первый запуск от обычного входа.
- `MASTER_PASSWORD_MIN_LENGTH = 8` — политика **ядра**, во фронте продублирована только
  чтобы подсветить проблему до отправки; ядро проверяет повторно (`VALIDATION`).
- Дев-переключатель `VITE_CORE_FRESH=1` — мок стартует без хранилища, UI уходит в онбординг.

## F4. Список паролей + поиск `[x]`
**Цель:** главный экран.
- Рендер записей по метаданным; поиск по `service_name` / `login` / `urls`.
- Группировка нескольких аккаунтов одного сервиса (визуально; различие по `login` / `account_label`), §4.4.
- Пустые состояния, состояние загрузки.
**Готово, когда:** мок-записи отображаются, поиск и группировка работают, **секретов в списке нет**.
**IPC:** `listRecords`.
**Стартовая точка:** после F3 `HomeView.vue` — каркас: шапка с блокировкой, плоский список
на `SyListItem`, пустое состояние. Поиска, группировки и сайдбара секций там ещё нет.

**Как сделано:**
- Логика списка — `src/composables/useRecordList.ts` (чистые функции + composable):
  `parseQuery` / `matchesQuery` / `normalizeHost` / `groupRecords`. Сначала фильтр,
  потом группировка — группа показывает только подошедшие под запрос аккаунты.
- Поиск идёт по `service_name`, `login`, `urls[]` **и** `account_label` (метка — то, чем
  пользователь различает аккаунты одного сервиса). Несколько слов работают как «И».
  Секреты не индексируются: в `RecordMeta` их нет по контракту — проверяется тестом.
- Группировка §4.4 — по **общему хосту** из `urls[]`, связывание транзитивное (union-find).
  «Регистрируемый домен» отбрасыванием поддоменов **не вычисляем**: без списка публичных
  суффиксов это склеило бы `foo.co.uk` и `bar.co.uk`. Недогруппировать безопаснее, чем
  угадать неверно. Запись без адресов группируется по имени сервиса и к записям с
  адресами не приклеивается. Заголовок группы рисуется только при ≥2 аккаунтах.
- Стор `useRecordsStore`: метаданные, строка поиска, `loading` / `loaded` / `error`.
  По событию `locked` список **очищается** — метаданные тоже содержимое хранилища и
  переживать блокировку не должны.
- Состояния экрана: скелет до первого ответа ядра (не спиннер — читается локальный файл),
  ошибка ядра, «Пока ни одного пароля», «Ничего не нашлось» + «Сбросить поиск».
  Счётчик «N записей · M сервисов» / «найдено N из M». Ctrl/Cmd + K — фокус в поиск,
  Esc — сброс.
- Сайдбар секций из макета — сознательно **не делали**: это F7.

## F5. Карточка записи + CRUD `[x]`
**Цель:** создание / просмотр / редактирование / удаление.
- Форма создания/редактирования (метаданные + секретные поля на ввод).
- **Reveal / копирование** секрета: разовый запрос в ядро, значение показывается временно, **не кладётся в стор**; авто-скрытие и очистка буфера по таймеру.
- Удаление → tombstone (UI отражает удаление; логика надгробий в ядре).
- Поле `totp_secret` в схеме есть; **генерацию TOTP-кодов не реализуем** (фаза 2), но поле сохраняем.
**Готово, когда:** полный CRUD против мока; reveal не оставляет секрет в состоянии (проверить тестом).
**IPC:** `createRecord`, `updateRecord`, `deleteRecord`, `getSecret`.

**Как сделано:**
- Экран стал **двухпанельным** (§3.1 макета): список 376 px слева, карточка/форма справа.
  Записи автоматически **не выбираются** — открывать чужую карточку без спроса менеджер
  паролей не должен. Строка списка стала кнопкой (мышь + клавиатура).
- Доступ к секретам — `useRecordSecrets` (`src/composables/useRecordSecrets.ts`): разовый
  `getSecret`, из ответа берётся **одно** поле, значение живёт в области видимости
  компонента (не в Pinia, не в localStorage) и исчезает по авто-скрытию (**30 с**), при
  смене записи, при размонтировании и по событию `locked`. Копирование секрета **не
  требует показа**.
- Буфер обмена — `useClipboard`: очистка через **20 с**, таймер **модульный**, чтобы
  обещание не ломалось от закрытия карточки; отсчёт вписан в кнопку (§4.5 макета), а не
  спрятан в тост. Чистим **безусловно, не сверяясь** с содержимым буфера: сверка требует
  держать секрет все 20 с — ровно то, чего избегаем. Блокировка хранилища чистит буфер
  немедленно.
- Компоненты: `SySecretField` (вариант A — маска **фиксированной длины**: длина пароля
  тоже сведения о секрете) и `SyCopyButton` (состояния idle · copied+отсчёт ·
  «Нечего копировать» · «Буфер недоступен»).
- Форма (`RecordForm.vue`) **не подтягивает секреты сама**. Пустое секретное поле в
  редактировании значит «оставить как было» — патч его не содержит. Чтобы дописать к
  заметке, есть кнопка «Показать текущее» — это такой же явный разовый reveal.
  Поле в патч попадает, только если значение реально изменилось: иначе каждое сохранение
  переписывало бы пароль и двигало `password_updated_at`.
- `totp_secret` — поле ввода и reveal есть, **генерации кодов нет** (фаза 2); в UI это
  сказано прямым текстом, а не притворством.
- Удаление: диалог с точными формулировками из макета + отдельное предупреждение про
  код подтверждения там, где он есть. Запись уходит из живого списка, ядро оставляет
  tombstone (§5.4).
- Селектора секции в форме **нет намеренно**: команд для vaults ещё нет в контракте — F7.
  Новая запись ложится в секцию по умолчанию. *(Появился в F7.)*

**Дополнено в контракте (нужно подтверждение бэкенд-агента):**
- `RecordMeta` получил два флага-**метаданных**: `has_notes` и `has_totp`. Это не секрет:
  флаг говорит «поле заполнено», но ничего не говорит о содержимом. Без них карточка не
  могла бы отличить «заметок нет» от «заметка есть, но скрыта», не запросив секрет, —
  то есть открывала бы секрет ради рисования рамки; и предупреждение про TOTP при удалении
  надо показать **до** удаления. Ядро считает флаги **у себя**, из самих секретов, а не
  принимает их от UI. У tombstone оба флага `false`.

## F6. Генератор паролей `[x]`
**Цель:** генерация с сохранённым профилем.
- Экран настроек профиля (набор символов, длина), сохраняется **один раз**.
- Запрос `n` вариантов → показ списка → выбор → в поле пароля.
**Готово, когда:** профиль сохраняется, `n` вариантов приходят из ядра, выбор проставляется.
**IPC:** `getGeneratorProfile`, `saveGeneratorProfile`, `generatePasswords(n)`.

**Как сделано:**
- Генерация целиком в **ядре**: во фронте нет ни алфавитов, ни случайности, ни
  подсчёта энтропии. UI шлёт правила и получает готовые строки. Фейк-ядро играет ту
  же роль — `src/core/mock/generator.ts`, случайность берёт у ОС
  (`crypto.getRandomValues`) с **отбраковкой хвоста** вместо `% n`: остаток от деления
  перекашивает алфавит, а это прямая потеря той стойкости, про которую рядом написано
  «≈ N бит».
- **Оценку энтропии считает ядро** и отдаёт в ответе. Фронт её не выводит сам: только
  ядро знает настоящий алфавит и размер словаря, а считать «на глаз» — врать
  пользователю о стойкости его пароля. Словарь мока маленький (20 слов), и оценка
  честно это отражает — 4 слова дают ≈17 бит, а не выдуманные 50.
- Два режима из §3.11 макета: **символы** и **слова** (парольная фраза). Поля обоих
  режимов лежат в профиле рядом, чтобы переключение не теряло уже настроенное.
  Буквы в алфавите есть всегда — профиля с пустым алфавитом не существует.
- Разделение ответственности: `useGeneratorStore` держит **только профиль** (это
  настройки, не секрет); сами варианты живут в `usePasswordGenerator` — в области
  видимости компонента. Поля под пароль в сторе нет по устройству, не «сейчас
  пусто» — проверяется тестом на ключи `$state`.
- **Авто-скрытия по таймеру у вариантов нет** — сознательно, в отличие от
  `useRecordSecrets`. Там таймер защищает чужой сохранённый пароль; здесь человек
  стоит и выбирает, и список, исчезающий из-под руки, мешал бы, ничего не защищая.
  Варианты уходят по закрытию панели, размонтированию и событию `locked`.
- Правки правил **не уходят в ядро сами**: §6.1 обещает профиль, настроенный один
  раз, — переписывать его на каждом движении ползунка было бы ровно наоборот. При этом
  предпросмотр считается по черновику (разовый профиль в запросе), чтобы последствия
  правки были видны **до** согласия на неё. Пересчёт с паузой 250 мс: ползунок длины
  шлёт событие на каждый шаг.
- В новой записи панель генератора открыта сразу (§6.1: «дальше в форме будет просто
  готовый пароль»), в редактировании — закрыта за кнопкой «Подобрать»: замена рабочего
  пароля должна быть осознанной. **Ни один вариант не подставляется сам** — выбор
  делает человек.
- Экран настроек `/settings` (§3.11) пока с одной секцией; под F7 (секции) и F12
  (данные/бэкапы) место оставлено, но пустых заглушек не рисуем. Закрыт замком
  наравне с паролями.

**Дополнено в контракте (нужно подтверждение бэкенд-агента):**
- Новые команды: `get_generator_profile`, `save_generator_profile { profile }`,
  `generate_passwords { count, profile? }` → `{ passwords, entropy_bits }`.
  Необязательный `profile` в запросе — разовые правила для предпросмотра; сохранённый
  профиль они **не меняют**. Все три требуют разблокированного хранилища.
- `GENERATOR_LIMITS` (длина 8–40, слов 3–7, вариантов 1–10) — политика **ядра**,
  во фронте продублирована ради границ ползунков; ядро проверяет повторно
  (`VALIDATION`), в том числе разовый профиль.
- **Исключение из Закона №1 в шапке `contract.ts`:** `generate_passwords` — вторая (и
  единственная кроме `get_secret`) команда, отдающая пароли открытым текстом. Это ещё
  ничей секрет, но правила обращения те же; зафиксировано в комментарии контракта.
- Профиль по умолчанию задаёт ядро (в моке — `DEFAULT_GENERATOR_PROFILE`); свежесозданное
  хранилище получает именно его.

## F7. Секции (vaults) + переключатель синхронизации `[x]`
**Цель:** организация и настройка синка по секциям.
- CRUD секций, привязка записи к секции.
- Тумблер «синхронизировать секцию / держать локальной» (§4.2).
**Готово, когда:** секции создаются, записи распределяются, флаг синка сохраняется.
**IPC:** `listVaults`, `createVault`, `setVaultSync`.

**Как сделано:**
- Секция — **фильтр, а не хранилище** (§4.2). В сайдбаре главного экрана
  (`SectionSidebar.vue`) первым стоит «Все записи» и выбрано по умолчанию: ключ
  у всех секций один, и по умолчанию они живут в одном пространстве. Фильтр
  лежит в `useRecordsStore.vaultFilter`, поиск и группировка §4.4 работают
  **внутри** выбранной секции.
- Экран управления — `/sections` (`SectionsView.vue`, §«Секции» макета):
  создание, переименование/цвет (`SectionEditor.vue`), назначение секции по
  умолчанию, тумблер синхронизации, удаление. Кнопка удаления секции
  **не красная**: красным помечается только то, после чего данные теряются, —
  а записи при удалении секции не пропадают.
- **Удаление секции не удаляет записи**: ядро переносит их в секцию по
  умолчанию, версия каждой растёт (на другом устройстве переезд должен
  выглядеть как правка). Секцию по умолчанию удалить нельзя — новым записям
  нужно куда-то попадать; в UI у неё просто нет этой кнопки, а ядро отвечает
  `VALIDATION`, если попросить.
- **Локальная секция названа локальной везде, где её видно**: пометка в
  сайдбаре, строка над списком, подпись у поля «Секция» в форме, подвал
  карточки («копии этой записи на других устройствах нет»). Про то, что пароль
  есть только на этом устройстве, человек должен узнавать до того, как на это
  понадеется, а не из настроек.
- Секция записи выбирается в форме (`SySelect`, нативный `<select>`): одна
  запись живёт ровно в одной секции. У новой записи предлагается та секция,
  что открыта в сайдбаре; если фильтра нет — поле показывает секцию по
  умолчанию, но `vault_id` в черновик **не кладётся**, и её выбирает ядро.
  В патч `vault_id` попадает, только если запись правда переставили.
- Стор `useSectionsStore` (назван по интерфейсному слову, чтобы не путать с
  `useVaultStore` — тот про замок). Состав секций — содержимое хранилища,
  поэтому по событию `locked` он очищается наравне со списком записей.
- Новые компоненты дизайн-системы: `SyToggle` (`role="switch"`, состояние
  словами рядом с ручкой; положение берётся из ответа ядра, а не из клика) и
  `SySelect`. Цвета меток — токены `--sy-vault-*` (в светлой теме темнее);
  на проводе живёт **имя** ступени палитры, а не CSS-цвет.

**Дополнено в контракте (нужно подтверждение бэкенд-агента):**
- Тип `Vault { vault_id, name, color, sync, is_default, created_at }` и
  `VaultColor` — имя ступени палитры (`indigo | amber | magenta | mint | coral`),
  а не CSS: оформление не должно попадать в синхронизируемые данные.
- Новые команды: `list_vaults`, `create_vault { name, color }`,
  `update_vault { vault_id, patch }` (имя и цвет), `set_vault_sync { vault_id, sync }`,
  `set_default_vault { vault_id }` → `Vault[]`, `delete_vault { vault_id }` → `Vault[]`.
  Все требуют разблокированного хранилища.
- **Флаг синхронизации вынесен из `update_vault` намеренно**: переименование —
  косметика, а этот тумблер решает, покидают ли записи устройство. Такое не
  меняют «заодно» с цветом.
- Команды, меняющие несколько секций сразу (`set_default_vault`,
  `delete_vault`), возвращают **весь список** — иначе UI пришлось бы гадать, с
  кого сняли флаг и что стало с записями.
- `delete_vault` **переносит записи** удалённой секции в секцию по умолчанию и
  инкрементирует их `version`; надгробия не трогаются (§5.4). Секция по
  умолчанию не удаляется (`VALIDATION`), помечена всегда ровно одна.
- `create_record` / `update_record` с неизвестным `vault_id` отвечают
  `NOT_FOUND`; без `vault_id` запись ложится в секцию по умолчанию.
- Новая секция создаётся **синхронизируемой** и не по умолчанию.
  Свежесозданное хранилище получает ровно одну секцию по умолчанию.
- `VAULT_NAME_MAX_LENGTH = 40` — политика **ядра**, во фронте продублирована
  ради `maxlength`; ядро проверяет повторно.

## F8. Сопряжение устройств (pairing) `[x]`
**Цель:** QR-обмен ключами (UI-часть).
- Показ QR со своим пейлоадом (данные готовит ядро) + экран сканирования QR.
- Скан на десктопе можно застабить / через файл; камера — где доступна.
**Готово, когда:** QR рендерится из мок-пейлоада, экран скана обрабатывает результат и шлёт в ядро.
**IPC:** `getPairingPayload`, `submitPairedKey`.

**Как сделано:**
- Экран `/devices` (`DevicesView.vue`, §3.6 макета): слева код или рамка ввода,
  справа — что происходит и что делать. Два режима, как в макете: «Показываю
  код» и «Ввожу код». Переключение в режим чтения **убирает свой код с
  экрана** — он там больше ни для чего не нужен.
- **QR кодирует ядро, а не фронт.** UI получает готовую матрицу (`QrMatrix`) и
  рисует квадратики (`PairingQr.vue`). Причина не в удобстве: в пейлоаде лежит
  одноразовый ключ сеанса, и чем меньше он существует отдельной JS-строкой, тем
  лучше. Проверяется тестом: в ответе `get_pairing_payload` четыре поля и
  никакого пейлоада. Заодно это снимает вопрос о QR-библиотеке во фронте —
  новых зависимостей не добавлено.
- **Сверку отпечатка нельзя пропустить.** `submit_paired_key` возвращает четыре
  слова и **не** делает устройство доверенным; запись происходит только в
  `confirm_pairing`, то есть после того, как человек сверил слова на двух
  экранах. Это единственная защита от MITM (§2.2), и «подтвердить за
  пользователя» здесь означало бы её отключить.
- **Камеру не изображаем.** Распознавание QR требует декодера в кадре — это
  мобильная часть (§9), и на десктопе камеры часто нет вовсе. Рамка со
  скользящей полоской, которая ничего не читает, заставила бы человека ждать
  впустую, поэтому рамка подписана честно, а рабочих пути два: набрать шесть
  символов или открыть файл с кодом (`PairingScanBox.vue`, чтение через
  `FileReader`).
- Код живёт **3 минуты**, отсчёт тикает на экране. Истёкший код с экрана **не
  убирается**, а гасится и перечёркивается: иначе непонятно, почему второе
  устройство его не берёт. «Обновить код» просит новый; прежний перестаёт
  действовать сразу, а не дожидается своего срока.
- Состояние сопряжения живёт в composable (`usePairing.ts`), **не в Pinia**: тот,
  кто прочитал код, получает право забрать копию хранилища — обращаемся с ним
  как с секретом. Код исчезает при уходе с экрана и по событию `locked`
  (проверяется тестом на `pinia.state`). Прочитанная строка уходит в ядро
  транзитом и в состоянии не оседает.
- На экране успеха — счётчики из ответа ядра, а не выдуманные. Если в хранилище
  есть локальная секция, рядом сказано прямым текстом, что её записи **не
  поехали**: обещание §4.2 должно выполняться и при сопряжении.
- Список доверенных устройств из макета — это **F9** (там же revoke); здесь его
  сознательно нет, заглушку не рисовали. Обратная сторона — уведомление тому,
  кто показывает код, что второе устройство сопряглось, — потребует событий
  ядра и делается вместе с F10.
- Тексты «сопряжение появится в будущих версиях» в `SetupView` заменены на
  ссылку на реальный экран.

**Дополнено в контракте (нужно подтверждение бэкенд-агента):**
- Новые типы: `Device`, `QrMatrix` (`{ size, rows }`, строки из `'0'`/`'1'`),
  `PairingOffer`, `PairingHandshake`, `PairingResult`.
- Новые команды: `get_pairing_payload` → `PairingOffer`,
  `submit_paired_key { payload }` → `PairingHandshake`,
  `confirm_pairing { session_id }` → `PairingResult`,
  `cancel_pairing { session_id }`. Все требуют разблокированного хранилища:
  код сопряжения даёт право забрать копию хранилища.
- `payload` — **одна строка**: UI не разбирает код и не знает его формата, он
  не отличает полный пейлоад из QR от шестизначного кода, набранного руками.
  Разбирает ядро, оно же отвечает `VALIDATION`, если это вообще не код Syncra.
- Новый код ошибки `PAIRING_EXPIRED` — устаревший код или сеанс. Отдельно от
  `VALIDATION` намеренно: «код истёк» и «код нечитаем» ведут пользователя к
  разным действиям.
- `records_transferred` **не считает записи локальных секций** (§4.2):
  выключенная синхронизация означает «никуда», в том числе на только что
  сопряжённое устройство.
- `cancel_pairing` идемпотентна; `confirm_pairing` — нет: сеанс одноразовый.
- Блокировка хранилища **отменяет незавершённые сопряжения** и аннулирует
  выданный код.
- Мок: код можно попробовать, введя любые шесть символов из алфавита
  `23456789ABCDEFGHJKLMNPQRSTUVWXYZ` (например, `4TQ9MB`) — фейк-ядро выдумает
  по нему второе устройство. Своим же кодом сопрячься нельзя.

## F9. Устройства + отзыв (revoke) `[x]`
**Цель:** управление доверенными устройствами.
- Список доверенных устройств; действие revoke с подтверждением.
**Готово, когда:** список из мока, revoke шлёт команду и обновляет UI.
**IPC:** `listDevices`, `revokeDevice`.

**Как сделано:**
- Список — в подвале того же `/devices` (`TrustedDevices.vue`), как в макете:
  «кто имеет доступ» и «дать доступ ещё одному» — один вопрос, и разносить их
  по разным экранам значило бы прятать половину ответа.
- **Подтверждение отзыва говорит, чего отзыв НЕ делает.** Формулировка из
  макета взята дословно: устройство перестанет получать обновления и не сможет
  сопрячься по старому ключу, но записи, которые оно уже скачало, остаются в
  его копии. §2.3 прямо предупреждает не переоценивать revoke — украденный
  ноутбук уже держит полную реплику на диске, и настоящая защита это шифрование
  at-rest. Поэтому рядом стоит совет, который правда помогает (сменить
  мастер-пароль и пароли важных сервисов), а не кнопка «стереть удалённо»,
  которой не существует.
- Подтверждение — **полоса внутри карточки**, а не модальное окно: отзыв читают
  рядом с тем устройством, у которого его отзывают, иначе легко ошибиться
  строкой. Кнопка «Отозвать доступ» — единственная красная на экране.
- **Отозванное устройство из списка не исчезает**, а гаснет с пометкой «доступ
  отозван»: отзыв — факт истории хранилища, и человек, отозвавший украденный
  ноутбук, должен видеть, что тот отозван, а не то, что его никогда не было.
- **Отменить отзыв нельзя, и команды для этого нет намеренно.** «Сопрячь
  заново» ведёт туда же, куда добавление любого устройства, — к показу кода:
  устройство, отрезанное по старому ключу, возвращается только через новый
  обмен ключами (§2.2), иначе отзыв не значил бы ничего.
- Себя отозвать нельзя — у своей карточки просто нет кнопки, а ядро отвечает
  `VALIDATION`, если попросить. Устройство, на котором открыт UI, — единственное,
  что у пользователя точно есть в руках.
- Пометка «давно не появлялся» (порог 30 дней, `deviceFormat.ts`) ничего не
  запрещает и ни на что не влияет: решение об отзыве принимает человек. У
  отозванного её нет — оно молчит потому, что его отрезали.
- Стор `useDevicesStore`: состав списка — содержимое хранилища («какими
  устройствами пользуется владелец»), поэтому по событию `locked` он очищается
  наравне с записями и секциями. Отказ ядра на конкретном устройстве летит
  исключением и показывается рядом с ним, а не гасит весь список.
- Сид фейк-ядра получил три устройства, и **их даты считаются от текущего
  времени**, а не зашиты константами, как у записей: список почти целиком про
  «когда виделись в последний раз», и зашитая дата через месяц разработки
  превратила бы каждое устройство в давно пропавшее.

**Дополнено в контракте (нужно подтверждение бэкенд-агента):**
- Новые команды: `list_devices` → `Device[]` и `revoke_device { device_id }` →
  `Device`. Обе требуют разблокированного хранилища: список устройств — такое же
  содержимое хранилища, как записи и секции.
- `list_devices` возвращает **и отозванные** устройства; отличать по `revoked_at`.
- `revoke_device` **идемпотентен**, и `revoked_at` при повторном вызове не
  переписывается: момент отзыва — факт, от которого считается, что успело
  разойтись по сети доверия, а что нет.
- Отзыв себя — `VALIDATION`, незнакомое устройство — `NOT_FOUND`.
- В ответе одно устройство, а не весь список (в отличие от `set_default_vault`):
  отзыв соседей не трогает.
- Команды «отменить отзыв» нет и не планируется (см. выше).
- Рассылка revoke-записи по сети доверия (§2.3) — целиком дело ядра; фейк-ядро
  её не изображает.

## F10. Статус синхронизации `[ ]`
**Цель:** видимость процесса.
- Состояния: idle / поиск пиров / синхронизация / ошибка; индикатор + время последнего синка.
- Подписка на события ядра.
**Готово, когда:** UI реагирует на мок-события смены состояния.
**IPC:** события `syncStatus`, `peerFound`.
**Стартовая точка:** после F9 есть `useDevicesStore` и `Device.last_seen_at` —
именно его двигают события синхронизации. Здесь же делается обратная сторона
F8: уведомление тому, кто показывал код, что второе устройство сопряглось.

## F11. Разрешение конфликтов `[ ]`
**Цель:** ключевой и тонкий экран.
- Полный diff двух версий записи; пользователь выбирает **одну версию целиком** (не по полям), §5.5.
- Показ, какая версия раньше / позже.
**Готово, когда:** мок отдаёт конфликт двух версий, выбор версии уходит в ядро.
**IPC:** событие `conflictRaised`, команда `resolveConflict(record_id, chosen_version)`.

## F12. Экспорт / импорт / бэкап `[ ]`
**Цель:** миграция и резервные копии.
- **CSV-экспорт:** после ввода мастер-пароля; **обязательное жёсткое предупреждение** «файл не зашифрован, удалите после использования» — формулировку не смягчать (§6.2).
- **Зашифрованный бэкап:** экспорт / восстановление файла (крипта — в ядре).
- **Импорт** из других менеджеров (CSV) — мастер импорта с превью.
**Готово, когда:** все три потока проходят против мока; предупреждение про CSV показывается и требует подтверждения.
**IPC:** `exportCsv`, `exportEncryptedBackup`, `importBackup`, `importCsv`.
